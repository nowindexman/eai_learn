## 概述

`rosidl::Buffer<T>` 是一种容器类型，用作生成的 C++ 消息中变长原始数组字段（`uint8[]`、`float32[]` 等）的内存表示。

它是 `std::vector<T>` 的直接替代品，同时支持可插拔的内存后端，因此 `uint8[]` 字段的数据可以存放在 CPU 内存、GPU 内存或供应商提供的任何其他内存域中——所有这些都不需要更改 `.msg` 文件或 ROS 2 消息管道的其余部分。

该功能的引入是为了让供应商能够通过现有的 ROS 2 发布/订阅 API 传输大型二进制数据（相机图像、点云、张量等），并尽可能减少底层内存技术所允许的拷贝次数，同时保持所有将 `uint8[]` 字段视为 `std::vector<uint8_t>` 的现有代码不变。

## 为什么需要新类型

ROS 2 消息已经有两种互补的减少拷贝的机制：

- [进程内通信](../../教程/演示/进程内通信.md) 通过传递 `std::unique_ptr` 所有权来避免同一进程内发布者和订阅之间的拷贝。
- [借用消息](../../操作指南/配置零拷贝借用消息.md) 让 RMW 管理消息内存，以实现进程间的共享内存传输，适用于底层中间件可以布局的消息类型。

当数据的*来源*是非 CPU 内存区域时（例如 GPU 渲染的图像或加速器运行时生成的张量），这两种方法都无济于事。仅仅为了满足生成的 C++ 消息类型而将此类数据复制到 `std::vector<uint8_t>` 中，就违背了在加速器上生成数据的初衷。

`rosidl::Buffer` 在容器层面解决了这个问题：在 `.msg` 文件中声明为 `uint8[]` 的消息字段在传输时仍然是字节数组，默认行为仍然像 `std::vector<uint8_t>`，但其实现是一个可插拔的 pimpl，后端可以用自己的内存域特定存储来替换。

## 架构

该功能分为三个核心包和一组可插拔的供应商提供的后端包。

### 核心包

- `rosidl_buffer` —— 定义用户面向的 `rosidl::Buffer<T>` 容器和 `rosidl::BufferImplBase<T>` 抽象基类（后端的父类）。`rosidl::Buffer<T>` 将所有操作转发给它持有的实现，并在活跃后端为 CPU 时提供到 `std::vector<T>&` 的隐式转换，这保持了向后兼容性。
- `rosidl_buffer_backend` —— 定义供应商实现的 `rosidl::BufferBackend` 插件接口。该接口刻意保持精简：它通告后端的名称和描述符消息类型，在发布和接收端创建和消费描述符消息，并参与端点发现。
- `rosidl_buffer_backend_registry` —— 通过 `pluginlib` 发现已安装的后端插件，并将它们暴露给协议栈的其余部分。

### 用户面向的容器和实现 pimpl

```text
┌──────────────────────────────┐
│     rosidl::Buffer<T>        │  (生成的消息持有的)
│  ┌────────────────────────┐  │
│  │ BufferImplBase<T>  ◄──-┼──┼── CpuBufferImpl<T>      (默认)
│  │ (pimpl)                │  │── CudaBufferImpl<T>     (供应商)
│  └────────────────────────┘  │── OtherBufferImpl<T>    (供应商)
└──────────────────────────────┘
```

新构造的 `rosidl::Buffer<T>` 使用 `CpuBufferImpl<T>`，它简单地包装了一个 `std::vector<T, Allocator>`。后端在分配缓冲区时（发布端）或从接收到的描述符重建时（订阅端）将其替换为自己的 `BufferImplBase<T>` 子类。

### 后端插件

`rosidl::BufferBackend` 插件是 RMW 层与之交互的对象。它的工作本质上是在内存中的 `BufferImplBase<T>` 和**描述符消息**之间进行转换——描述符消息是一个普通的 ROS 2 `.msg`，描述如何在接收端定位或重建有效载荷。

对于纯 CPU 后端，描述符可以直接携带字节数据。对于非 CPU 后端，描述符通常是一个小型引用，接收端用它来重新连接到有效载荷；具体机制取决于后端实现。

描述符消息是有界的（`rosidl::kMaxBufferDescriptorSize`，4096 字节），以便 RMW 可以预先规划序列化缓冲区大小。

## 描述符往返与RMW集成

当发布者发送包含具有非 CPU 后端的 `rosidl::Buffer<T>` 字段的消息时，RMW：

1. 请求后端为当前对端构建描述符（`create_descriptor_with_endpoint`）；
2. 将描述符序列化以替代原始 `uint8[]` 字节；
3. 在订阅端，反序列化描述符并请求后端从中重建 `BufferImplBase<T>`（`from_descriptor_with_endpoint`）。

### 发现钩子

后端通过 `on_creating_endpoint`（本地）和 `on_discovering_endpoint`（远程）获知每个匹配的端点。它们使用这些钩子来决定给定的发布/订阅对是否真正与后端的传输兼容。例如，CUDA 后端目前仅在接受方可以安全共享 CUDA VMM 分配时才接受对端。如果后端无法服务某个特定对端，它从 `create_descriptor_with_endpoint` 返回 `nullptr`，RMW 将回退到该字段的普通 CPU 序列化。

### RMW 无关的插件契约

插件接口本身是 RMW 无关的。`BufferBackend::get_descriptor_type_support()` 返回通用的 `rosidl_message_type_support_t *` 聚合句柄（与 `rosidl_typesupport_cpp::get_message_type_support_handle<T>()` 生成的句柄相同），用于后端的描述符消息类型。消费方 RMW 将该聚合解析为它在运行时需要的具体 per-typesupport 库。当前的 `rmw_fastrtps_cpp` 集成将此聚合解析为 `rosidl_typesupport_fastrtps_cpp`，但后端 API 中没有任何内容将其绑定到特定 RMW。

## 后端与高层库

后端应表示一种内存基底或传输技术。示例包括基于 CUDA VMM 和 CUDA IPC 构建的 CUDA 后端、ROCm 后端或共享内存后端。后端知道如何分配内存、将该内存打包成描述符，以及在另一个端点重新导入它。

更高层的数据模型可以作为普通消息和库存在于这一层之上。例如，`tensor_msgs/msg/ExperimentalTensor` 携带 DLPack 对齐的张量元数据（dtype、shape、strides、字节偏移）加上一个 `uint8[] data` 字段。该 `data` 字段在生成的 C++ 代码中是一个 `rosidl::Buffer<uint8_t>`，因此可以由连接协商的任何后端来传输。`torch_conversions` 辅助库在 `ExperimentalTensor` 和 `at::Tensor` 之间进行转换；它本身不是缓冲区后端。当消息的数据缓冲区使用 `cuda` 后端时，张量字节可以通过 CUDA IPC 移动。当使用 CPU 后端时，相同的消息和辅助 API 仍然适用于普通主机内存。

## 与其他ROS 2机制的关系

- `rosidl::Buffer` 与[进程内通信](../../教程/演示/进程内通信.md)和[借用消息](../../操作指南/配置零拷贝借用消息.md)是正交的。后端可以为给定的发布/订阅对实现其中任一种、两者都实现或都不实现；决定完全在后端内部。
- 给定的发布者/订阅者对是否实际可以使用非 CPU 传输（进程内、进程间同主机、跨主机等）取决于后端实现的属性，而非 `rosidl::Buffer`。请查阅每个后端自己的文档了解其支持矩阵。
- `.msg` IDL 不变：之前是 `uint8[]` 的字段仍然是 `uint8[]`；只是其生成的 C++ 类型从 `std::vector<uint8_t>` 变为 `rosidl::Buffer<uint8_t>`，隐式转换使大多数现有代码继续工作。
- 当前的 RMW 集成适用于话题发布/订阅。服务和动作继续使用其正常的序列化路径，不协商非 CPU 缓冲区后端。

## 与类型适配的关系

`rosidl::Buffer` 后端在生成的消息容器层运行。ROS 消息定义仍然是话题类型，而选定的变长原始数组字段可以使用后端特定的存储和基于描述符的传输。

类型适配和 Isaac ROS NITROS 等系统解决的是不同的问题：它们让应用程序代码使用框架原生类型，并在 ROS 消息类型之上协商适配表示，使用 [REP 2007](https://reps.openrobotics.org/rep-2007/) 和 [REP 2009](https://reps.openrobotics.org/rep-2009/) 等机制。这两种方法不是同一抽象的一部分，也不打算相互依赖；它们的范围不同。当两者都有用时，它们可以在应用程序中共存。例如，一个适配的应用程序类型仍然可以包含或生成一个 ROS 消息，其 `uint8[]` 字段由 `rosidl::Buffer` 支持。

一个实际区别是缓冲区后端对 RMW 发布/订阅路径可见，因此后端可以提供跨进程传输支持，而类型适配只能在单个进程内工作。
