# ROS 2 开发者指南

本页面定义了我们开发 ROS 2 时遵循的实践和政策。

## 通用原则

所有 ROS 2 开发共有的几个原则：

- **共享所有权**：每个参与 ROS 2 开发的人都应该对系统的所有部分感到拥有感。代码块的原作者没有任何特殊权限或义务来控制或维护该代码块。每个人都可以自由地在任何地方提出更改、处理任何类型的工单和审查任何拉取请求。

- **愿意承担任何工作**：作为共享所有权的必然结果，每个人都应该愿意承担任何可用任务并为系统的任何方面做出贡献。

- **寻求帮助**：如果您在某些事情上遇到困难，请通过工单、评论或电子邮件等适当方式向其他开发者寻求帮助。

## 质量实践

包可以根据其遵循的开发实践归入不同的质量级别，按照 [REP 2004：包质量分类](https://reps.openrobotics.org/rep-2004/) 的指南。分类根据版本控制、测试、文档等策略进行区分。

以下是我们为确保核心包达到最高质量（'Level 1'）而遵循的具体开发规则。我们建议所有 ROS 开发者努力遵循以下策略，以确保整个 ROS 生态系统的质量。

### 生成式 AI 的使用

在向 ROS 代码或文档做任何类型的贡献时，必须遵循 [OSRF 政策](https://osralliance.org/wp-content/uploads/2025/05/OSRF-Policy-on-the-Use-of-Generative-Tools-Generative-AI-in-Contributions.pdf)关于使用生成式 AI 的规定。

### 版本控制

我们使用[语义化版本控制指南](http://semver.org/)（`semver`）进行版本管理。

同时遵循一些基于 semver 完整含义之上的 ROS 特定规则：

- **主版本递增**（即破坏性更改）不应在已发布的 ROS 发行版内进行
- **补丁版本**（接口保留）和**次版本**（非破坏性）递增不会破坏兼容性，因此在发行版内是允许的
- **主版本 ROS 发布**是发布破坏性更改的最佳时机

### 更改控制流程

所有更改应通过拉取请求进行，并经过代码审查。

### 文档

所有公共 API 必须有文档。文档包括：
- API 参考文档
- 用户指南
- 变更日志

### 测试

所有核心包必须有测试，包括：
- 单元测试
- 集成测试
- 性能测试（适用时）

## 通用实践

### 分支策略

- 主要开发在 `rolling` 分支上进行
- 已发布发行版的修补在其对应分支上进行

### 包命名约定

- 包名应使用 `snake_case`
- 包名应该是描述性的和唯一的

### 度量和坐标系约定

- 使用 SI 单位制
- 坐标系遵循 [REP 103](https://www.ros.org/reps/rep-0103.html) 标准约定

## 开发者工作流

1. Fork 目标仓库
2. 创建功能分支
3. 进行更改并编写测试
4. 确保所有测试通过
5. 提交拉取请求
6. 响应审查反馈

## 架构开发实践

### 软件开发生命周期

ROS 2 遵循标准的软件开发生命周期：
1. 设计和规划
2. 实现
3. 测试
4. 发布
5. 维护
