# 01：数据流水线架构

## 1. 分层而不是一个巨型脚本

推荐的最小处理链路：

| 阶段 | 输入 | 输出 | 允许修改原始数据吗 |
|---|---|---|---|
| `inspect` | bag/MCAP | 结构、计数、时间和工具报告 | 不允许 |
| `parse` | 原始消息 | 消息级 JSONL/中间对象 | 不允许 |
| `normalize` | 消息级记录 | 统一时间、单位、字段和 frame | 不允许 |
| `align` | 多 topic 表 | 对齐表、匹配误差和 mask | 不允许 |
| `quality` | 中间结果 | 指标、问题和等级 | 不允许 |
| `dataset` | 通过门禁的数据 | Parquet、图像索引、manifest | 只写派生目录 |

这样做的意义是：容器格式问题、消息解码问题、同步问题和训练数据问题可以分别定位。`ros2 bag convert` 或 `mcap filter` 只是其中某个工具步骤，不能替代整个语义流水线。

## 2. 输入、输出和失败契约

每个阶段都要回答：

```text
输入是什么？
输入是否完整？
输出路径如何确定？
输出成功如何证明？
失败后能否安全重跑？
```

例如 `normalize` 的输出契约可以是：

```text
必须有：episode_id、time_ns、time_basis、source_topic、source_sha256
JointState 必须有：joint_name_order_version、position_unit、frame_id
图像索引必须有：path、log_time_ns、decode_ok、width、height
```

字段缺失应使阶段失败或产生显式 warning，不要用空字符串掩盖“未知”。

## 3. 配置驱动

把会变化的选择写到配置文件，代码只负责执行：

```yaml
schema_version: "dataset-1"
time:
  basis: header_stamp_ns
  fallback: log_time_ns
  image_tolerance_ns: 20000000
topics:
  state: /robot/joint_states
  action: /robot/cmd_vel
  images:
    - /camera/head/image
quality:
  min_image_decode_rate: 0.99
  max_negative_timestamp_jumps: 0
output:
  format: parquet
  write_images: true
```

这份 YAML 是项目配置，不是 MCAP 规范，也不是 rosbag2 自动生成的 `metadata.yaml`。配置文件本身应纳入版本控制，运行时要把实际配置复制到 manifest 中。

## 4. 目录布局与路径安全

建议把源文件相对路径、输入校验和和输出命名规则结合起来：

```text
data/raw/run_002/                         # 原始输入
data/derived/dataset-1/run_002/           # 派生结果
reports/run_002.inspect.json
reports/run_002.quality.json
manifests/run_002.manifest.json
```

输出路径必须落在明确的派生根目录，不要让输入文件名直接拼接成任意路径。文件名来自用户或 bag 记录时，要做路径规范化并阻止 `..` 穿越。

## 5. 处理门禁

可以把阶段状态画成简单的门禁：

```text
发现输入
  ↓ inspect 通过
读取/解码
  ↓ 类型与抽样通过
规范化/同步
  ↓ 时间、单位、frame 检查通过
质量门禁
  ├─ error → rejected + 报告
  └─ pass/warning → dataset + manifest
```

warning 是否允许进入数据集必须由配置决定；例如图像缺帧可能允许用于调试数据，但不允许进入要求全观测的训练集。

## 6. 本篇练习

1. 画出自己数据的五个阶段和每阶段输出。
2. 为一个状态 topic 和一个图像 topic 写配置。
3. 明确哪些问题应该在 `inspect` 阶段发现，哪些只能在解码/语义阶段发现。
4. 设计一个“输出已存在但校验和不匹配”的处理策略：停止、隔离或重新生成，都必须记录。
