# 03.5：具身智能常见 ROS 消息 Schema 与 `msg_type`

> 本文是第一周的消息类型速查，不试图列出 ROS 的全部接口。选择的类型依据是：具身智能机器人在采集“本体状态、控制动作、视觉观察、空间关系、任务与系统信息”时经常出现，并且适合后续转换为训练数据。
>
> 下面以 ROS 1 Noetic 与 ROS 2 Jazzy 的标准接口为主。具体发行版、驱动包或厂商包可能增加字段或使用自定义类型，最终仍应以实际环境中的 `rosmsg show` / `ros2 interface show` 和 MCAP 内的 schema 为准。

## 1. 先分清 `msg_type`、schema 和消息数据编码

同一个消息至少要看三个维度：

| 维度 | 示例 | 它回答的问题 |
|---|---|---|
| 类型名（`msg_type`） | ROS 1：`sensor_msgs/JointState`；ROS 2：`sensor_msgs/msg/JointState` | 这条消息按哪一种接口解释？ |
| schema encoding | `ros1msg`、`ros2msg` | 消息结构定义用什么形式描述？ |
| message encoding | ROS 1 常见 `ros1`；ROS 2 常见 `cdr` | 消息字段实际如何序列化成字节？ |

在 ROS 2 写入的 MCAP 中，常见组合是：

```text
profile:              ros2
schema.name:          sensor_msgs/msg/JointState
schema.encoding:      ros2msg
channel.message_encoding: cdr
```

这四项不是同一件事：`profile` 是文件级提示，`schema` 描述字段结构，`message_encoding` 描述每条消息的字节布局。`mcap info` 的 channel 行中显示的 `[ros2msg]` 是 schema encoding，不等于 `cdr`；`ros2 bag info` 通常会额外显示 `Serialization Format: cdr`。

## 2. ROS 1 与 ROS 2 的类型名对应关系

ROS 2 把消息、服务、动作分别放到 `msg`、`srv`、`action` 命名空间中，因此命令行中多了这一层：

| 接口类别 | ROS 1 写法 | ROS 2 写法 |
|---|---|---|
| 消息 | `geometry_msgs/Twist` | `geometry_msgs/msg/Twist` |
| 服务 | `std_srvs/SetBool` | `std_srvs/srv/SetBool` |
| 动作 | `control_msgs/FollowJointTrajectoryAction` 等 | `control_msgs/action/FollowJointTrajectory` |

本文主要讨论消息（topic 中传输的 `msg`）。在 `.msg` 定义的字段中，嵌套类型通常仍写成 `std_msgs/Header header`；不要把命令行里的完整名称 `std_msgs/msg/Header` 原样塞进 `.msg` 字段定义。命令行查看时则使用完整 ROS 2 类型名：

```bash
# ROS 1
rosmsg show sensor_msgs/JointState

# ROS 2
ros2 interface show sensor_msgs/msg/JointState
ros2 topic type /robot/joint_states
```

## 3. 按具身智能数据链路选择常见类型

没有一个由 ROS 官方规定的“具身智能消息类型白名单”。下面是工程上更有代表性的优先级：

| 数据环节 | 优先掌握的标准类型 | 常见话题示例 | 典型用途 |
|---|---|---|---|
| 本体状态 | `JointState`、`Imu`、`Odometry`、`BatteryState` | `/joint_states`、`/imu`、`/odom` | 关节、惯导、位姿、底盘状态 |
| 控制与动作 | `Twist`、`PoseStamped`、`JointTrajectory`、`WrenchStamped` | `/cmd_vel`、`/arm_controller/command` | 速度、目标位姿、关节轨迹、力/力矩 |
| 视觉观察 | `Image`、`CompressedImage`、`CameraInfo` | `/camera/...` | 原始图像、压缩图像、相机标定 |
| 空间与环境 | `TFMessage`、`TransformStamped`、`PointCloud2`、`LaserScan` | `/tf`、`/tf_static`、`/points`、`/scan` | 坐标变换、点云、激光 |
| 任务与系统 | `String`、`Bool`、`Clock`、日志/参数事件 | `/task_state`、`/clock` | 阶段标签、仿真时间、系统上下文 |

`vision_msgs/Detection2DArray`、`vision_msgs/Detection3DArray`、`control_msgs` 中的控制器接口也很常见，但它们依赖具体感知/控制栈，不应冒充所有机器人都必备的基础类型。真实系统还经常使用厂商自定义消息。

## 4. 核心消息结构

以下代码块展示的是 `.msg` 层面的字段结构。ROS 1 与 ROS 2 中，大多数消息字段语义相同；区别主要在完整类型名、序列化方式，以及少数历史字段命名。

### 4.1 `Header`：时间戳与坐标系的基础

| 版本 | 完整类型名 | 定义 |
|---|---|---|
| ROS 1 | `std_msgs/Header` | `uint32 seq`、`time stamp`、`string frame_id` |
| ROS 2 | `std_msgs/msg/Header` | `builtin_interfaces/Time stamp`、`string frame_id` |

```text
# ROS 1 std_msgs/Header
uint32 seq
time stamp
string frame_id
```

```text
# ROS 2 std_msgs/msg/Header
builtin_interfaces/Time stamp
string frame_id
```

| 字段 | 含义 |
|---|---|
| seq（仅 ROS 1） | 发布者维护的消息序号，通常递增，用于调试丢包或重复消息；它不是时间，也不能作为跨 topic 的同步依据。 |
| stamp | 消息时间戳。ROS 1 的 time 和 ROS 2 的 builtin_interfaces/Time 都由秒和纳秒组成；它通常表示传感器采集或消息生成时间，不一定等于 bag 的 log_time。 |
| stamp.sec / stamp.nanosec | 时间戳的秒和纳秒部分。转换为 Unix 纳秒或其他单位时，必须先统一时间基准和单位，不能只取 sec。 |
| frame_id | 数据所属的坐标系名称，例如 base_link、imu_link、camera_optical_frame。它只标识坐标系，不负责提供坐标变换；变换关系要从 TF 中获取。 |

要点：

- ROS 1 的 `seq` 在 ROS 2 的 `Header` 定义中已移除；DDS 内部序号也不是 `header.stamp` 的替代品。
- `header.stamp` 是消息生产者写入的消息时间，bag 的 `log_time` 是记录器写入/记录时使用的时间；两者可能不同。
- `frame_id` 是解释空间数据所需的坐标系名称。没有它，位姿、IMU、图像和力数据可能无法正确对齐。

### 4.2 `sensor_msgs/JointState`：关节本体状态

| ROS 1 | ROS 2 |
|---|---|
| `sensor_msgs/JointState` | `sensor_msgs/msg/JointState` |

```text
std_msgs/Header header
string[] name
float64[] position
float64[] velocity
float64[] effort
```

| 字段 | 含义 |
|---|---|
| header | 这组关节状态的时间戳和参考坐标系。关节状态是否使用某个具体 frame_id，要看机器人驱动的约定。 |
| name | 关节名称数组，是关节数据的索引基准。name[i] 对应 position[i]、velocity[i]、effort[i]。 |
| position | 关节位置；旋转关节通常是弧度，移动关节通常是米。它表示实际测量状态还是控制器估计值，要看发布者。 |
| velocity | 关节速度；旋转关节通常是 rad/s，移动关节通常是 m/s。没有发布时可以为空。 |
| effort | 关节所受或施加的力/力矩；旋转关节通常是 N·m，移动关节通常是 N。具体是测量值、命令值还是估计值要核对驱动文档。 |

- `name[i]` 与对应数组的同一索引表示同一个关节。
- 标准定义要求各数组要么长度一致，要么为空；实际数据中 `velocity`、`effort` 可能没有发布。
- 常见单位是 `position` 用弧度、`velocity` 用弧度/秒、`effort` 用 N·m，但转换数据集时仍应核对驱动器和机器人约定。
- 不能把所有 `JointState` 都当成同一种语义：`/joint_states` 可能是全身状态，`/hand_left/joints` 可能只是手部状态，`/finger_force` 甚至可能借用该类型承载触觉数值。要结合话题名、关节名和发布节点判断。

### 4.3 `sensor_msgs/Imu`：惯性测量

| ROS 1 | ROS 2 |
|---|---|
| `sensor_msgs/Imu` | `sensor_msgs/msg/Imu` |

```text
std_msgs/Header header
geometry_msgs/Quaternion orientation
float64[9] orientation_covariance
geometry_msgs/Vector3 angular_velocity
float64[9] angular_velocity_covariance
geometry_msgs/Vector3 linear_acceleration
float64[9] linear_acceleration_covariance
```

| 字段 | 含义 |
|---|---|
| header | IMU 测量的时间和坐标系。angular_velocity、linear_acceleration 等向量通常都在 header.frame_id 坐标系中表达。 |
| orientation | IMU 或融合算法估计的姿态四元数，字段为 x、y、z、w；它描述传感器坐标系相对参考坐标系的旋转，具体方向要按系统约定理解。 |
| orientation_covariance | 姿态估计误差的 3×3 协方差矩阵，按行展开为 9 个数。若没有姿态估计，标准约定是将第一个元素设为 -1。 |
| angular_velocity | 绕 x、y、z 轴的角速度，通常单位为 rad/s。 |
| angular_velocity_covariance | 角速度误差的 3×3 协方差矩阵，按行展开；没有角速度估计时同样检查第一个元素的约定。 |
| linear_acceleration | 沿 x、y、z 轴的线加速度，通常单位为 m/s²；是否包含重力要看 IMU 驱动和配置。 |
| linear_acceleration_covariance | 线加速度误差的 3×3 协方差矩阵，按行展开；它不是加速度本身。 |

- `angular_velocity` 常用单位是 rad/s，`linear_acceleration` 常用单位是 m/s²。
- 三个协方差数组都是按行展开的 3×3 矩阵；不能只读取数值而丢掉协方差。
- `orientation` 是否有效、是否由融合算法产生，要结合协方差约定和驱动文档判断；消息类型本身不保证传感器一定提供姿态解算。

### 4.4 `nav_msgs/Odometry`：带参考系的里程计

| ROS 1 | ROS 2 |
|---|---|
| `nav_msgs/Odometry` | `nav_msgs/msg/Odometry` |

```text
std_msgs/Header header
string child_frame_id
geometry_msgs/PoseWithCovariance pose
geometry_msgs/TwistWithCovariance twist
```

| 字段 | 含义 |
|---|---|
| header | 里程计消息的时间和父坐标系。通常 header.frame_id 是 odom 或其他世界/里程计坐标系。 |
| child_frame_id | 被描述的子坐标系，通常是 base_link。它不是另一个时间戳，而是字符串形式的 TF frame 名称。 |
| pose | 在 header.frame_id 中表达的位姿及其 6×6 协方差。pose.pose.position 是位置，pose.pose.orientation 是姿态。 |
| pose.pose.position | 三维位置 x/y/z，通常单位为米。 |
| pose.pose.orientation | 描述朝向的四元数 x/y/z/w。 |
| pose.covariance | 位姿误差协方差，36 个数按 6×6 矩阵行展开；通常对应 x、y、z、绕 x、绕 y、绕 z 的误差顺序。 |
| twist | 在 child_frame_id 中表达的线速度和角速度及其协方差。 |
| twist.twist.linear | 子坐标系下的线速度 x/y/z，通常单位为 m/s。 |
| twist.twist.angular | 子坐标系下的角速度 x/y/z，通常单位为 rad/s。 |
| twist.covariance | 速度误差协方差，36 个数按 6×6 矩阵行展开。 |

通常 `header.frame_id` 是父坐标系（例如 `odom`），`child_frame_id` 是机器人本体坐标系（例如 `base_link`）。`pose` 与 `twist` 各自带 6×6 协方差；不能只把位置和速度六个数抽出来就认为里程计信息完整。

### 4.5 `geometry_msgs` 与 `trajectory_msgs`：动作、目标和力

#### `geometry_msgs/Twist`

| ROS 1 | ROS 2 |
|---|---|
| `geometry_msgs/Twist` | `geometry_msgs/msg/Twist` |

```text
geometry_msgs/Vector3 linear
geometry_msgs/Vector3 angular
```

| 字段 | 含义 |
|---|---|
| linear | 三维线速度或线速度目标，内部有 x、y、z 三个分量，通常单位为 m/s。 |
| linear.x / linear.y / linear.z | 分别表示沿消息参考坐标系 x、y、z 轴的线速度；在底盘控制中常见 x 前进、y 横移、z 竖直，但要以机器人坐标约定为准。 |
| angular | 三维角速度或角速度目标，内部有 x、y、z 三个分量，通常单位为 rad/s。 |
| angular.x / angular.y / angular.z | 分别表示绕 x、y、z 轴的角速度；不要把 z 轴角速度默认当成所有机器人的“转向速度”。 |

常见于 `/cmd_vel`。但 `Twist` 只规定字段，不规定它一定是“控制命令”；同样的类型也可能表示测得的速度，最终语义取决于话题和发布者。

#### `geometry_msgs/PoseStamped`

| ROS 1 | ROS 2 |
|---|---|
| `geometry_msgs/PoseStamped` | `geometry_msgs/msg/PoseStamped` |

```text
std_msgs/Header header
geometry_msgs/Pose pose
```

| 字段 | 含义 |
|---|---|
| header | 位姿的时间戳和参考坐标系。position 和 orientation 都是在 header.frame_id 中表达的。 |
| pose | 位姿复合字段，包含 position 和 orientation。 |
| pose.position | 位置点，包含 x、y、z，通常单位为米。 |
| pose.orientation | 姿态四元数，包含 x、y、z、w；不能把它当成欧拉角的 roll、pitch、yaw。 |

`pose.position` 是三维位置，`pose.orientation` 是四元数。它常用于末端目标、导航目标或视觉估计结果；使用时必须同时保留时间戳和 `frame_id`。

#### `geometry_msgs/WrenchStamped`

| ROS 1 | ROS 2 |
|---|---|
| `geometry_msgs/WrenchStamped` | `geometry_msgs/msg/WrenchStamped` |

```text
std_msgs/Header header
geometry_msgs/Wrench wrench
```

| 字段 | 含义 |
|---|---|
| header | 力/力矩的采样时间和参考坐标系。力和力矩的方向必须结合 header.frame_id 解释。 |
| wrench | 力和力矩的复合字段。 |
| wrench.force | 三维力 x、y、z，通常单位为 N。 |
| wrench.torque | 三维力矩 x、y、z，通常单位为 N·m。 |

其中 `Wrench` 为：

```text
geometry_msgs/Vector3 force
geometry_msgs/Vector3 torque
```

常见于足底力、腕部六维力传感器和接触检测。力的参考坐标系由 `header.frame_id` 决定，不能忽略。

#### `trajectory_msgs/JointTrajectory`

| ROS 1 | ROS 2 |
|---|---|
| `trajectory_msgs/JointTrajectory` | `trajectory_msgs/msg/JointTrajectory` |

```text
std_msgs/Header header
string[] joint_names
JointTrajectoryPoint[] points
```

`JointTrajectoryPoint` 的关键字段如下：

```text
float64[] positions
float64[] velocities
float64[] accelerations
float64[] effort
```

```text
# ROS 1
duration time_from_start

# ROS 2
builtin_interfaces/Duration time_from_start
```

| 字段 | 含义 |
|---|---|
| header | 轨迹消息的参考时间和坐标系。很多控制器把 header.stamp 作为轨迹起始时间，值为 0 时可能表示从当前时刻开始，具体以控制器约定为准。 |
| joint_names | 轨迹涉及的关节名称及固定顺序；每个轨迹点的数组都必须按这个顺序解释。 |
| points | 按时间排列的轨迹点数组，每个点包含一组期望位置、速度、加速度和力矩。 |
| points[i].positions | 第 i 个轨迹点的期望关节位置；可以为空，但若提供，长度应与 joint_names 一致。 |
| points[i].velocities | 第 i 个点的期望关节速度；可为空，通常单位为 rad/s 或 m/s。 |
| points[i].accelerations | 第 i 个点的期望关节加速度；可为空，单位取决于关节类型。 |
| points[i].effort | 第 i 个点的期望力/力矩；可为空，旋转关节通常为 N·m，移动关节通常为 N。 |
| points[i].time_from_start | 从轨迹起始时刻到该点的相对时长。ROS 1 用 duration，ROS 2 用 builtin_interfaces/Duration；它不是 Unix 时间戳。 |

每个点的数组要与 `joint_names` 的顺序对应。它表达的是期望轨迹或控制器输入，不等于机器人实际执行到的关节状态；训练数据中应区分 action 与 observation。

### 4.6 `sensor_msgs`：图像与相机标定

#### `sensor_msgs/Image`

| ROS 1 | ROS 2 |
|---|---|
| `sensor_msgs/Image` | `sensor_msgs/msg/Image` |

```text
std_msgs/Header header
uint32 height
uint32 width
string encoding
uint8 is_bigendian
uint32 step
uint8[] data
```

| 字段 | 含义 |
|---|---|
| header | 图像采集时间和图像坐标系。时间可能接近曝光时间，也可能是驱动生成消息的时间，要结合相机驱动确认。 |
| height | 图像高度，单位是像素，表示有多少行。 |
| width | 图像宽度，单位是像素，表示每行有多少个像素。 |
| encoding | 原始像素布局和数据类型，例如 rgb8、bgr8、mono8、16UC1；它决定每个像素占多少字节、通道顺序和数值类型。 |
| is_bigendian | 多字节像素数据的字节序标志；对单字节像素通常没有影响，但解析 16 位或 32 位像素时不能忽略。 |
| step | 一行像素占用的字节数，也叫行步长；它可能因为内存对齐大于 width 乘以单像素字节数。 |
| data | 未压缩的原始像素字节。正常情况下长度应为 step 乘以 height；不能把它直接当成 JPEG 或 PNG 文件。 |

这是原始像素消息。`encoding` 例如 `rgb8`、`bgr8`、`mono8`、`16UC1`；`step` 是每行字节数，`data` 不是默认的 JPEG/PNG 文件。解析图像必须同时处理宽高、编码、步长、大小端和字节数组。

#### `sensor_msgs/CompressedImage`

| ROS 1 | ROS 2 |
|---|---|
| `sensor_msgs/CompressedImage` | `sensor_msgs/msg/CompressedImage` |

```text
std_msgs/Header header
string format
uint8[] data
```

| 字段 | 含义 |
|---|---|
| header | 压缩图像的时间和坐标系。它应与对应原始图像或相机数据保持可关联的时间/坐标语义。 |
| format | 压缩格式和原始像素格式的提示，例如 jpeg、png 或带有 raw 编码信息的组合字符串；它不是对字节内容的完整校验。 |
| data | 压缩后的文件字节，例如 JPEG/PNG 字节流。宽高、通道数等信息通常需要解码后才能可靠得到。 |

`data` 通常是 JPEG 或 PNG 等压缩字节，`format` 是格式提示而不是完整的文件格式证明。解码后还要检查实际宽高、通道顺序和颜色空间。

#### `sensor_msgs/CameraInfo`

这是 ROS 1/ROS 2 中最值得特别记忆的标准消息之一：字段语义基本相同，但矩阵字段大小写不同。

```text
# ROS 1 sensor_msgs/CameraInfo
std_msgs/Header header
uint32 height
uint32 width
string distortion_model
float64[] D
float64[9] K
float64[9] R
float64[12] P
uint32 binning_x
uint32 binning_y
RegionOfInterest roi
```

```text
# ROS 2 sensor_msgs/msg/CameraInfo
std_msgs/Header header
uint32 height
uint32 width
string distortion_model
float64[] d
float64[9] k
float64[9] r
float64[12] p
uint32 binning_x
uint32 binning_y
RegionOfInterest roi
```

| 字段 | 含义 |
|---|---|
| header | 标定信息适用的时间和相机坐标系；通常应与对应图像的 header.frame_id 关联。 |
| height | 标定参数对应的图像高度，单位为像素。 |
| width | 标定参数对应的图像宽度，单位为像素；如果图像经过裁剪或缩放，不能盲用原始分辨率的标定。 |
| distortion_model | 畸变模型名称，例如 plumb_bob、rational_polynomial 或 equidistant；它决定 D/d 数组的系数含义和顺序。 |
| D / d | 畸变系数数组。长度不是固定的，由 distortion_model 决定；ROS 1 使用大写，ROS 2 使用小写。 |
| K / k | 3×3 原始图像内参矩阵，按行展开，通常形如 [fx, 0, cx, 0, fy, cy, 0, 0, 1]。fx、fy 是焦距，cx、cy 是主点。 |
| R / r | 3×3 校正/旋转矩阵，按行展开；用于把相机坐标变换到校正后的相机坐标，单目场景通常接近单位矩阵。 |
| P / p | 3×4 投影矩阵，按行展开；用于把三维相机坐标投影到校正后的图像平面，双目相机还会包含基线相关项。 |
| binning_x | 水平方向像素合并或降采样的倍数；它会影响有效分辨率和内参，具体无 binning 时的 0/1 表示以驱动实现为准。 |
| binning_y | 垂直方向像素合并或降采样的倍数；与 binning_x 一起决定标定参数适用的采样方式。 |
| roi | 感兴趣区域，表示相机实际使用的图像子区域；它不是普通的目标检测框。 |

RegionOfInterest 的字段为：

~~~text
uint32 x_offset
uint32 y_offset
uint32 height
uint32 width
bool do_rectify
~~~

| ROI 字段 | 含义 |
|---|---|
| x_offset | ROI 左上角相对于原图左边界的水平偏移，单位为像素。 |
| y_offset | ROI 左上角相对于原图上边界的垂直偏移，单位为像素。 |
| height / width | ROI 的高度和宽度，单位为像素；为 0 往往表示没有设置有效 ROI，但要结合驱动约定。 |
| do_rectify | 是否要求节点在处理时使用该 ROI 进行图像校正。 |

其中 `K`/`k` 是内参矩阵，`R`/`r` 是校正矩阵，`P`/`p` 是投影矩阵，`D`/`d` 是畸变参数。必须把它与对应图像 topic、时间和 `frame_id` 关联，不能把一份标定参数无条件应用到所有相机或所有时间段。

### 4.7 `tf2_msgs` 与环境感知消息

#### `geometry_msgs/TransformStamped` 与 `tf2_msgs/TFMessage`

```text
# geometry_msgs/TransformStamped
std_msgs/Header header
string child_frame_id
geometry_msgs/Transform transform
```

```text
# tf2_msgs/TFMessage
geometry_msgs/TransformStamped[] transforms
```

| 字段 | 含义 |
|---|---|
| header | 变换生效的时间和父坐标系。header.frame_id 是 parent frame，不能只看 child_frame_id。 |
| child_frame_id | 被描述的子坐标系名称，例如 base_link 或 camera_link。 |
| transform | 从 header.frame_id 到 child_frame_id 的平移和旋转关系。 |
| transform.translation | 三维平移 x、y、z，通常单位为米。 |
| transform.rotation | 三维旋转四元数 x、y、z、w；它不是欧拉角。 |
| transforms | TFMessage 中的变换数组；一条 TFMessage 可以同时携带多条 TransformStamped。 |

| ROS 1 | ROS 2 |
|---|---|
| `geometry_msgs/TransformStamped` | `geometry_msgs/msg/TransformStamped` |
| `tf2_msgs/TFMessage` | `tf2_msgs/msg/TFMessage` |

`/tf` 通常发布动态变换，`/tf_static` 通常发布静态变换。回放或转换时要保留它们，否则图像、点云、末端位姿可能无法变换到同一坐标系。`Transform` 内部是 `translation` 和 `rotation`，旋转通常用四元数。

#### `sensor_msgs/PointCloud2`

| ROS 1 | ROS 2 |
|---|---|
| `sensor_msgs/PointCloud2` | `sensor_msgs/msg/PointCloud2` |

```text
std_msgs/Header header
uint32 height
uint32 width
PointField[] fields
bool is_bigendian
uint32 point_step
uint32 row_step
uint8[] data
bool is_dense
```

| 字段 | 含义 |
|---|---|
| header | 点云的采集时间和点坐标所属坐标系。点的 x/y/z 必须在这个 frame_id 中解释。 |
| height | 点云组织形式的行数。无组织点云通常为 1；有组织点云可以对应深度图的高度。 |
| width | 每行点数；无组织点云中通常等于点总数，有组织点云中表示每行的列数。 |
| fields | 每个点包含哪些字段以及字段在二进制 data 中的布局，例如 x、y、z、intensity。 |
| is_bigendian | data 中多字节数值的字节序标志。 |
| point_step | 一个点占用的字节数，包括该点各字段和可能的填充。 |
| row_step | 一行点占用的字节数，通常等于 point_step 乘以 width，也可能包含行填充。 |
| data | 所有点的打包二进制数据；要依据 fields、point_step、row_step 解析，不能直接按 float 数组强转。 |
| is_dense | 是否保证点云中没有 NaN 等无效点；false 时必须检查每个点的有效性。 |

PointField 的字段为：

~~~text
string name
uint32 offset
uint8 datatype
uint32 count
~~~

| PointField 字段 | 含义 |
|---|---|
| name | 字段名称，例如 x、y、z、rgb、intensity。 |
| offset | 从一个点的起始字节到该字段起始位置的偏移。 |
| datatype | 字段数据类型枚举，例如 INT8=1、UINT8=2、INT16=3、UINT16=4、INT32=5、UINT32=6、FLOAT32=7、FLOAT64=8。 |
| count | 每个点中该字段包含的元素数量；普通 x/y/z 通常为 1。 |

`PointCloud2` 不是“每个点一个固定 ROS 对象”的数组，而是按 `fields`、`offset`、`datatype`、`count` 描述的打包二进制。要读取 `x/y/z/intensity`，必须按字段描述解释 `data`，不能仅凭 `width` 和 `height` 猜布局。

#### `sensor_msgs/LaserScan`

| ROS 1 | ROS 2 |
|---|---|
| `sensor_msgs/LaserScan` | `sensor_msgs/msg/LaserScan` |

```text
std_msgs/Header header
float32 angle_min
float32 angle_max
float32 angle_increment
float32 time_increment
float32 scan_time
float32 range_min
float32 range_max
float32[] ranges
float32[] intensities
```

| 字段 | 含义 |
|---|---|
| header | 扫描时间和激光坐标系。header.stamp 通常表示扫描开始或第一条射线的采集时间，具体以驱动实现为准。 |
| angle_min | 扫描起始角，单位为弧度。 |
| angle_max | 扫描结束角，单位为弧度。 |
| angle_increment | 相邻两条射线之间的角度增量，单位为弧度。第 i 条射线角度通常为 angle_min + i × angle_increment。 |
| time_increment | 相邻两条射线的采集时间间隔，单位为秒；运动时可用于补偿扫描期间的位姿变化。 |
| scan_time | 两次完整扫描之间的时间间隔，单位为秒。 |
| range_min | 有效测距下限，单位为米；小于该值的 ranges 通常视为无效。 |
| range_max | 有效测距上限，单位为米；大于该值的 ranges 通常视为无效。 |
| ranges | 每条射线的距离数组，单位为米；NaN、无穷值或越界值需要按无效数据处理。 |
| intensities | 每条射线的反射强度数组，单位由雷达/激光器决定；设备不提供时可能为空。 |

`ranges[i]` 对应由角度参数计算出的第 `i` 条射线。无效测距可能表现为 `NaN` 或无穷值，不能只按数组长度判断数据有效。

### 4.8 任务、仿真时间和电源信息

#### `std_msgs/String` 与简单标量

| ROS 1 | ROS 2 |
|---|---|
| `std_msgs/String` | `std_msgs/msg/String` |

```text
string data
```

| 字段 | 含义 |
|---|---|
| data | 字符串内容。它可能是任务阶段、场景名、状态文本或调试信息；消息定义不提供枚举、时间戳、单位、来源和版本，必须由话题约定或外部 manifest 补充。 |

它常被用来快速发布任务阶段、场景名或调试标签。但 `String` 不携带枚举定义、时间语义、单位和版本；长期数据集最好设计明确的自定义消息或在 manifest 中记录字段约定。`std_msgs/Bool`、`std_msgs/Float32` 等简单标量也有同样问题。

#### 其他常见类型

| 类型 | ROS 1 | ROS 2 | 说明 |
|---|---|---|---|
| 仿真时钟 | `rosgraph_msgs/Clock` | `rosgraph_msgs/msg/Clock` | 字段为 `clock`；不能和消息自身的 `header.stamp` 混为一谈 |
| 电池状态 | `sensor_msgs/BatteryState` | `sensor_msgs/msg/BatteryState` | 电压、电流、容量、电量百分比和电芯信息 |
| 路径 | `nav_msgs/Path` | `nav_msgs/msg/Path` | `PoseStamped[] poses`，常用于导航轨迹或规划结果 |
| 2D 检测 | `vision_msgs/Detection2DArray` | `vision_msgs/msg/Detection2DArray` | 感知栈统一输出之一，具体字段和检测器语义仍需核对 |
| 3D 检测 | `vision_msgs/Detection3DArray` | `vision_msgs/msg/Detection3DArray` | 适用于目标的三维检测结果，不是原始点云替代品 |

## 5. 厂商自定义消息：具身智能中同样重要

标准消息覆盖通用通信结构，但机器人真正的任务数据经常来自自定义接口，例如：

- 灵巧手关节、夹爪开合和电机电流；
- 触觉阵列、足底接触、碰撞状态；
- 机器人模式、任务阶段、成功/失败标签；
- 规划器输出、策略网络 action、控制器诊断；
- 多模态采集器的 episode_id、时间同步状态和设备序列号。

自定义类型可能长这样：

```text
# ROS 1: my_robot_msgs/HandState
# ROS 2: my_robot_msgs/msg/HandState
std_msgs/Header header
string[] joint_names
float64[] position
float64[] velocity
float32[] tactile
uint8 mode
```

这里的完整类型名可以看起来像 `JointState`，但只要字段、单位或数组语义不同，就不能当作标准 `sensor_msgs/JointState` 解码或直接拼接。处理自定义消息至少要保存：

1. 完整类型名和 `.msg`/IDL 定义；
2. ROS 发行版、包版本或源码提交号；
3. 字段单位、坐标系、关节顺序和枚举含义；
4. 话题名、发布节点、QoS（ROS 2）以及时间戳约定。

## 7. 学习时的最小核对流程

对一个新 bag 或 MCAP，建议按以下顺序核对：

```bash
# 1. 看 ROS 2 bag 的 topic、类型、数量和序列化格式
ros2 bag info <bag_uri>

# 2. 查看类型定义
ros2 interface show sensor_msgs/msg/JointState
ros2 interface show sensor_msgs/msg/CameraInfo

# 3. 看正在运行的 topic 类型和实际字段
ros2 topic type /robot/joint_states
ros2 topic echo --once /robot/joint_states

# 4. 独立检查 MCAP 的 channel/schema
mcap info <file.mcap>
mcap list channels <file.mcap>
mcap list schemas <file.mcap>
```

验收时至少记录：

- ROS 1/ROS 2 完整类型名；
- `schema.encoding` 与 `message_encoding`；
- `log_time` 与 `header.stamp` 的时间单位和差异；
- 数组长度、关节顺序、图像编码、单位和 `frame_id`；
- 自定义消息的定义来源和版本。
