# 第四篇：概念对比与第一周总结

这一篇只做边界梳理：rosbag1、rosbag2 和 MCAP 不是三个完全同层级的格式。rosbag1 是 ROS 1 的记录格式；rosbag2 是 ROS 2 的录制框架，实际数据由存储后端保存；MCAP 既可以作为 rosbag2 的存储后端，也可以独立承载多种编码的日志。

## 一、三者定位对比

| 特性 | rosbag1（ROS 1） | rosbag2（ROS 2） | MCAP |
|---|---|---|---|
| 定位 | ROS 1 录制工具与 `.bag` 文件 | ROS 2 录制/回放框架 | 开放式日志容器格式 |
| 运行依赖 | 命令行录制/回放通常需要 ROS Master；离线查看可不启动 `roscore` | ROS 2 节点和存储插件；不依赖 `roscore` | 读取容器本身不要求 ROS；解码消息仍可能需要 ROS 类型支持 |
| 常见形态 | 单个 `.bag` 文件 | bag URI 目录，通常含 `metadata.yaml` 和一个或多个后端文件 | 一个 `.mcap` 文件，也可以是 rosbag2 目录中的存储文件 |
| 类型信息 | 连接头中通常有类型名、MD5 和消息定义文本等信息，但反序列化仍需要兼容的 ROS 类型代码 | 元数据通常有类型名、序列化格式、QoS 等；具体字段随版本和后端变化 | 可记录 schema，也允许没有 schema；schema 是否完整取决于写入端 |
| 序列化 | ROS 1 专用序列化 | 常见为 CDR，也可能受具体存储/转换能力影响 | 可承载 ROS 1、CDR、JSON、Protobuf 等多种 message encoding |
| 索引与访问 | 有索引结构；异常中断后可能需要 `reindex` | 访问能力取决于存储后端和元数据是否完整 | 可有 summary/index，具备时便于定位；没有时仍可顺序读取 |
| 随机访问 | 工具和索引支持有限，不能把所有访问都理解为 O(1) | 不同后端能力不同，不能只由“rosbag2”三个字判断 | 有索引时适合按时间定位，但不是所有文件都含完整索引 |
| 多编码 | 主要围绕 ROS 1 消息 | 主要围绕 ROS 2 类型和序列化 | 容器层支持多编码，解码器必须匹配具体编码 |
| 典型用途 | ROS 1 存量数据、遗留系统回放 | ROS 2 采集、回放、转换 | 跨语言处理、可视化、长期归档和数据管线中间格式 |

## 二、不要混淆的四个概念

### 1. 文件扩展名不等于消息编码

`.mcap` 只能说明容器格式，不能直接说明消息是 JSON、ROS 1 二进制还是 ROS 2 CDR。应先看：

```bash
mcap info sample.mcap
mcap list channels sample.mcap
mcap list schemas sample.mcap
```

看到 `message_encoding: cdr` 时，仍需要 ROS 2 类型定义或可用的 CDR 解码器；看到 `json` 时，才可能直接用通用 JSON 工具处理。

### 2. schema、profile、library 不是一回事

- `schema` 描述消息结构；它可以是 `ros1msg`、`ros2msg`、`jsonschema`、`protobuf` 等编码。
- `message_encoding` 描述每条消息的序列化方式，例如 `ros1`、`cdr`、`json`。
- `profile` 是 MCAP Header 中的规范提示，例如 `ros1` 或 `ros2`，不是消息的完整定义。
- `library` 是写入端留下的实现信息，便于追踪生成工具，不是解码器。

因此，文件里有 schema 也不代表任何工具都能解码；工具还必须理解对应的 schema encoding 和 message encoding。

### 3. metadata、索引和数据内容是三层东西

话题名、类型、时间范围、消息数量属于元数据；用于快速定位的 summary/index 属于访问辅助结构；真正的消息字节属于数据内容。`ros2 bag reindex` 或 `mcap recover` 主要处理元数据/结构，不能凭空恢复已经没有的消息。

### 4. “能播放”不等于“数据正确”

播放器能打开文件，只能说明容器和部分类型信息可用。还要检查时间戳是否合理、话题是否齐全、消息数量是否符合预期、QoS/TF/单位/坐标系是否正确，以及图像和动作是否能被实际解码。

## 三、第一周验收任务

1. 用 `rosbag record` 录制一段 ROS 1 话题，用 `rosbag info` 查看消息数量、时间范围和类型，再用 `rosbag play` 回放。
2. 用 `ros2 bag record` 录制一段 ROS 2 数据，记录它生成的 bag URI、`metadata.yaml`、存储后端和序列化格式；不要假定后端一定是 SQLite3 或 MCAP。
3. 对一个 MCAP 文件执行 `mcap info`、`mcap doctor`、`mcap list schemas`，再用 `mcap filter` 生成话题子集。`mcap cat --json` 只对支持的编码使用。
4. 能用自己的话回答：
   - 为什么 `ros2 bag` 这个命令可以生成 `.mcap`？
   - 为什么只有一个 `.mcap` 文件时，不能据此断定元数据缺失？
   - 为什么一个带 `cdr` 的 MCAP 文件仍可能需要 ROS 2 类型定义？

## 四、第一周应留下的记录

为每个练习文件记录以下信息：

```text
输入路径：
文件/目录形态：
工具与版本：
ROS 发行版（如适用）：
存储后端：
话题与类型：
message encoding / schema encoding：
起止时间与消息数量：
是否正常收尾、是否通过 doctor/info：
```

这张记录表比死记某个发行版的默认参数更重要，因为同一个命令在不同 ROS 发行版、存储插件和工具版本下可能展示不同字段。
