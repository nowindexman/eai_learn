## 第一部分：rosbag 概念与命令行速通

### 1. 什么是 rosbag？

rosbag 是 ROS 生态中用来记录和回放“话题消息”的工具。它本质上是一个**日志文件**，按时间顺序存储了 ROS 计算图中流通的消息。

- **rosbag v1**（ROS 1 时代）：文件扩展名 `.bag`，内部是自定义二进制格式，消息类型定义（.msg 文件）需要外置或嵌入。
- **rosbag v2**（ROS 2 时代）：默认使用 SQLite3 数据库存储，扩展名也是 `.bag` 但其实是 SQLite 文件（可以用 `sqlite3` 命令打开查看）。通过插件机制，**也可以直接使用 MCAP 作为存储后端**，此时扩展名通常为 `.mcap`。

### 2. rosbag v1 核心命令

> **前置条件**：rosbag v1 的所有命令都依赖 `roscore`（ROS 主节点）。先启动容器，后台运行 roscore，再执行后续操作。
> 否则会报 `Failed to contact master at [localhost:11311]`。

```bash
# 启动容器（挂载当前目录到 /data）
docker run -it --rm --name ros1_lab -v $(pwd):/data ros:noetic-ros-base bash

# 更新包列表并安装 Python3 + pip + OpenCV + NumPy  （用于相机图像模拟）
apt-get update && apt-get install -y python3-pip && pip3 install opencv-python-headless numpy

# 容器内执行：初始化环境 + 后台启动 roscore
source /opt/ros/noetic/setup.bash
roscore &
sleep 2
```

#### ROS 消息通用结构（用 `rosmsg show` 查看）

用 `rosmsg show` 可以查看任何消息类型的完整字段定义：
```bash
rosmsg show sensor_msgs/JointState
rosmsg show sensor_msgs/CompressedImage
rosmsg show nav_msgs/Odometry
```

##### 基本数据类型

| ROS 类型 | 对应 Python | 对应 C++ | 说明 |
|---------|-----------|---------|------|
| `bool` | `bool` | `bool` | 真/假 |
| `int8` / `uint8` | `int` | `int8_t` / `uint8_t` | 8 位整数，uint8 也用于表示字节数据 |
| `int16` / `uint16` | `int` | `int16_t` / `uint16_t` | 16 位整数 |
| `int32` / `uint32` | `int` | `int32_t` / `uint32_t` | 32 位整数 |
| `int64` / `uint64` | `int` | `int64_t` / `uint64_t` | 64 位整数 |
| `float32` | `float` | `float` | 单精度浮点 |
| `float64` | `float` | `double` | 双精度浮点（ROS 中角度/位置默认用这个） |
| `string` | `str` | `std::string` | 字符串 |
| `time` | `rospy.Time` | `ros::Time` | 时间戳（secs + nsecs） |
| `duration` | `rospy.Duration` | `ros::Duration` | 时间间隔（secs + nsecs） |

##### 数组类型

```bash
# 动态数组（长度可变）
float64[] position    # ← JointState 的关节角度，长度 = 关节数
string[] name         # ← 关节名称列表
uint8[] data          # ← CompressedImage 的图像字节

# 固定数组（长度写死）
float64[36] covariance  # ← Odometry 的协方差矩阵，6×6 展平 = 36 个元素
float64[9] K            # ← CameraInfo 的内参矩阵，3×3 展平 = 9 个元素
float64[12] P           # ← CameraInfo 的投影矩阵，3×4 展平 = 12 个元素
```

##### 通用结构：`std_msgs/Header`

几乎所有 ROS 消息都包含一个 `header` 字段，它是消息的“身份证”：

```bash
std_msgs/Header header
  uint32 seq          # 消息序号，自增（第几条消息）
  time stamp          # 时间戳（精确到纳秒）
  string frame_id     # 坐标系名称（数据是在哪个参考系下测量的）
```

**三个字段的作用：**

| 字段 | 作用 | 示例 |
|------|------|------|
| `seq` | 消息序号，用于检测丢包 | `0, 1, 2, ... 2465` |
| `stamp` | 时间戳，用于多传感器时间对齐 | `1780625604.850000000` |
| `frame_id` | 坐标系，用于 TF 坐标变换 | `"odom"`, `"base_link"`, `"head_camera_link"` |

**frame_id 的实际含义：**
```
机器人坐标系树（TF Tree）：

  odom
   └── base_link        ← 躯干中心
        ├── l_hip_link   ← 左髓
        ├── r_hip_link   ← 右髓
        ├── torso_imu    ← IMU 传感器的 frame_id
        ├── head_camera_link  ← 头部相机的 frame_id
        └── wrist_camera_link ← 手腕相机的 frame_id
```

**哪些消息有 Header，哪些没有：**

| 消息类型 | 有 Header | 原因 |
|---------|---------|------|
| `sensor_msgs/Imu` | ✅ | 传感器数据必须有时间戳 |
| `sensor_msgs/JointState` | ✅ | 关节状态必须有时间戳 |
| `sensor_msgs/CompressedImage` | ✅ | 图像必须有时间戳 |
| `nav_msgs/Odometry` | ✅ | 里程计需要时间戳 + 坐标系 |
| `geometry_msgs/Twist` | ❌ | 纯速度指令，不需要时间戳 |
| `std_msgs/String` | ❌ | 简单文本，不需要 |
| `std_msgs/Float64` | ❌ | 单个数值，不需要 |

> **规则**：带时间、空间属性的传感器数据都有 Header；简单的控制指令、状态文本通常没有。

##### 实际例子对比

```bash
# JointState（带 Header，有数组）
$ rosmsg show sensor_msgs/JointState
  std_msgs/Header header     ← 有 header
    uint32 seq
    time stamp
    string frame_id
  string[] name              ← 关节名称列表（动态数组）
  float64[] position         ← 关节角度（动态数组）
  float64[] velocity         ← 关节速度（动态数组）
  float64[] effort           ← 关节力矩（动态数组）

# CompressedImage（带 Header，有字节数组）
$ rosmsg show sensor_msgs/CompressedImage
  std_msgs/Header header     ← 有 header
    uint32 seq
    time stamp
    string frame_id
  string format              ← 压缩格式（"jpeg" / "png"）
  uint8[] data               ← 图片二进制数据（字节数组）

# Twist（无 Header，纯数据）
$ rosmsg show geometry_msgs/Twist
  geometry_msgs/Vector3 linear   ← 无 header，只有 x/y/z
    float64 x
    float64 y
    float64 z
  geometry_msgs/Vector3 angular  ← 角速度 x/y/z
    float64 x
    float64 y
    float64 z
```

##### 嵌套类型

消息可以嵌套其他消息类型，像俄罗斯套娃：

```
nav_msgs/Odometry
  └── geometry_msgs/PoseWithCovariance pose
        ├── geometry_msgs/Pose pose          ← 嵌套 Pose
        │     ├── Point position             ← 嵌套 Point
        │     └── Quaternion orientation     ← 嵌套 Quaternion
        └── float64[36] covariance
  └── geometry_msgs/TwistWithCovariance twist
        ├── geometry_msgs/Twist twist        ← 嵌套 Twist
        └── float64[36] covariance
```

> 在 Python 中访问：`msg.pose.pose.position.x`，就是层层点进去。

#### 录制数据：`rosbag record`

```bash
# 先后台启动录制，再运行发布脚本
nohup rosbag record -a -O /data/demo.bag > /tmp/rosbag.log 2>&1 &
sleep 1
python3 /data/publish_demo.py
# Ctrl+C 停止发布，然后停掉录制
pkill -f 'rosbag record'
```

也可以手动分步操作：
```bash
# 进入容器
docker exec -it ros1_lab bash

# 录制所有话题 
# 没结束之前都是 zyw_2026-06-05-02-13-11.bag.active 这种形态的 
# 结束之后才会去掉active
rosbag record -a

# 录制指定话题，输出文件名由 -O 指定
rosbag record -O my_record.bag /sensor/status /sensor/temperature

# 录制时自动切分：每200MB或每10分钟切一个文件
rosbag record --split --size=200 --duration=10m /scan
```

常用参数释义：
- `-a`：录制所有正在发布的话题。
- `-O`：指定输出文件名（不加 .bag 会自动补上）。
- `--split`：按大小或时间切分，适合长时间采集。
- `--duration=10m`：录制10分钟后自动停止。
- `-j`：压缩（`bz2` 或 `lz4`），后面会提到。

#### 字段逐项解释

| 字段 | 示例值 | 含义 |
|------|--------|------|
| **path** | `zyw_2026-06-05-...bag` | 文件路径。`zyw` 是 `-O` 指定的前缀，后自动加时间戳 |
| **version** | `2.0` | bag 格式版本。ROS 1 固定为 2.0（v1.0 是远古版本） |
| **duration** | `49.8s` | 录制时长 = end - start。约 2 个完整任务循环 |
| **start** | `Jun 05 2026 ... (1780625604.85)` | 第一条消息的时间戳：人类可读 + Unix 时间戳 |
| **end** | `Jun 05 2026 ... (1780625654.68)` | 最后一条消息的时间戳 |
| **size** | `13.8 MB` | 文件体积，包含消息数据 + 索引 + 消息定义 |
| **messages** | `24374` | 所有话题的消息条数之和 |
| **compression** | `none [18/18 chunks]` | 压缩方式。`none`=未压缩，`18/18`=共 18 个 chunk 全未压缩。chunk 是 bag 内部存储单元，默认约 768KB/个。用 `--lz4` 或 `--bz2` 可启用压缩 |
| **types** | `geometry_msgs/Twist [9f195f...]` | 用到的所有消息类型 + MD5 校验和。MD5 由消息定义文件计算，**同一版本 ROS 全球统一不变**，用于防止类型不匹配 |
| **topics** | 每行一个话题 | 话题名、消息数、消息类型 |
| **msgs** | `2466 msgs` | 该话题在录制期间收到的总消息数 |
| **(N connections)** | `(2 connections)` | 有多少个不同节点向该话题发布消息。没标注=默认 1 个。`/rosout` 有 2 个：publish_demo.py + rosbag 自身 |

#### 回放数据：`rosbag play`

```bash
# 正常速度回放
rosbag play /data/demo.bag

# 5倍速回放，只发布传感器话题
rosbag play /data/demo.bag --rate=5 --topics /sensor/status /sensor/temperature

# 从第30秒开始，播放5秒内容
rosbag play my_record.bag --start=30 --duration=5
```

实际输出：

回放时，消息会按录制时的相对时间间隔重新发布到 ROS 网络中，就像时光倒流一样。

#### 更多常用命令

##### 文件检查：`rosbag check`

检查 bag 文件是否损坏，对比内部 MD5 与当前系统是否一致：
```bash
rosbag check demo.bag
```
输出示例（正常）：
```
demo.bag is good.
```
输出示例（有问题）：
```
The following migrations need to occur:
  from: sensor_msgs/JointState  [old_md5]
  to:   sensor_msgs/JointState  [new_md5]
```
> 通常在 ROS 版本升级后消息定义变了才会出现。日常采集不会遇到。

##### 压缩与解压：`rosbag compress` / `decompress`

```bash
# 压缩为 lz4（推荐，速度快，压缩率约 40-60%）
rosbag compress --lz4 demo.bag
# 生成 demo.bag.lz4.bag，原文件保留

# 压缩为 bz2（压缩率更高，但慢）
rosbag compress --bz2 demo.bag

# 解压（play 也能自动解压，一般不需要手动解压）
rosbag decompress demo.bag.lz4.bag
```
> **实际经验**：50Hz 的 56 关节 + 双相机，1 分钟原始数据约 20-30 MB，lz4 压缩后约 8-12 MB。

##### 修复索引：`rosbag reindex`

录制过程中容器崩溃或 `kill -9` 强杀，bag 索引可能没写完：
```bash
# 修复损坏的 bag 文件
rosbag reindex broken.bag
# 生成 broken.bag.reindex.bag，原文件保留

# 修复后验证
rosbag info broken.bag.reindex.bag
```

##### 实时查看话题：`rostopic`

录制过程中实时监控：
```bash
# 查看某话题的实时消息（每秒刷新）
rostopic echo /robot/task_state

# 查看某话题的实际发布频率
rostopic hz /robot/joint_states
# 输出：average rate: 49.987  min: 0.019s  max: 0.021s

# 列出所有正在发布的话题
rostopic list

# 查看某话题的消息类型
rostopic type /robot/odom
# 输出：nav_msgs/Odometry

# 查看某话题一条消息的完整字段
rostopic echo /robot/odom --noarr  # --noarr 省略数组，输出更简洁
```

##### 实时查看节点：`rosnode`

```bash
# 列出所有运行中的节点

```

不用打开源码就能看任何消息类型的完整定义：
```bash
# 查看 Odometry 的全部字段
```

### 3. rosbag v2 核心命令

在 ROS 2 容器中操作，格式类似但命令前缀变为 `ros2 bag`。

#### 录制
```bash
# 默认以 SQLite 格式录制所有话题
ros2 bag record -a -o my_bag

# 明确指定使用 MCAP 格式存储
ros2 bag record -a -o my_bag --storage mcap

# 只录特定话题，并设置切分大小
ros2 bag record /scan /tf -o scan_data --max-bag-size 100000000
```
注意：输出文件夹 `my_bag` 里包含 `metadata.yaml` 和数据库文件（如 `.db3` 或 `.mcap`）。`-a` 在 ROS 2 中需要守护进程正在运行并发布话题。

#### 查看信息
```bash
ros2 bag info my_bag
```
输出会比 rosbag v1 更结构化，会列出存储 ID（sqlite3 或 mcap）、消息数量等。

#### 回放
```bash
ros2 bag play my_bag
```
回放同样支持 `--rate`、`--topics` 过滤等。

#### 格式转换
rosbag v2 内置了转换工具，可以直接将 SQLite 的 bag 转为 MCAP 格式：
```bash
ros2 bag convert -i my_bag -o output_bag --output-version 9 --output-storage mcap
```
这个命令在数据处理管线中非常实用，因为 MCAP 对跨语言、云存储更友好。

## 第二部分：MCAP 概念与命令行深入

### 1. MCAP 是什么？为什么重要？

MCAP（Metadata Capable Application Protocol）是 Foxglove 公司设计的**机器人数据记录文件格式**。它从设计之初就解决了 rosbag 的几个痛点：

- **自描述性**：消息 schema（定义）直接内嵌在文件里，无需外部 `.msg` 文件。
- **可索引、随机访问**：文件尾部有摘要区，可以快速跳到任意时间点读取，不需要顺序扫描整个文件。
- **多编码支持**：消息可以用 JSON、Protobuf、FlatBuffers、ROS 1/2 原生格式等多种编码，非常灵活。
- **流式友好**：支持边写边读，适合机器人实时上传到云端的场景。
- **压缩与分块**：内置分块机制，可对每个块独立压缩（如 lz4、zstd），读取时不需要解压整个文件。
- **语言无关**：官方提供 C++、Python、JavaScript、Go 等库，没有 ROS 也能用。

文件结构大致为：
```
[Magic][Header][Data Chunks...][Summary Section][Magic][Footer]
```
这种结构让 MCAP 可以成为一个“可自愈”的格式，即使在写入过程中崩溃，也很容易修复。

### 2. MCAP 命令行工具 `mcap`

安装后直接使用 `mcap` 命令，主要子命令：

#### `mcap info` – 查看元数据
```bash
mcap info sample.mcap
```
输出示例：
```
library: mcap
profile: x
messages: 1234
channels: 2
  (1) /odom 1000 msgs (1000.0 Hz)
  (2) /scan 234 msgs (10.0 Hz)
... 
file size: 2.3 MB
```
你会看到每个通道（相当于话题）的消息数量、平均频率、消息编码等。这对于数据处理系统在读取前快速判断文件内容非常有价值。

#### `mcap cat` – 将消息输出为 JSON Lines
```bash
# 打印所有消息的 JSON 表示
mcap cat sample.mcap

# 只输出某个通道，并且限制行数
mcap cat sample.mcap --topic /odom | head -n 5
```
每行一条消息的 JSON，便于用 `jq` 或日志处理工具分析。注意：消息数据本身会按照其编码形式（如 JSON、protobuf 序列化后的 bytes）呈现，如果是二进制格式会显示为 base64 字符串。

#### `mcap filter` – 按条件切出新文件
```bash
# 只保留 /odom 通道，生成 new.mcap
mcap filter sample.mcap -o new.mcap --include-topic /odom

# 保留多个通道，并限定时间范围
mcap filter big.mcap -o slice.mcap --include-topic "/odom" --include-topic "/tf" \
    --start-sec 1600000000 --end-sec 1600000010
```
这在处理系统里可以用来从海量数据中截取一小段进行分析，而不必读取整个大文件。

#### `mcap compress` / `decompress` – 压缩与解压
```bash
mcap compress uncompressed.mcap -o compressed.mcap --zstd
mcap decompress compressed.mcap -o original.mcap
```

#### `mcap list schemas` – 查看文件中注册的 schema
```bash
mcap list schemas sample.mcap
```
这对理解数据格式、转换成其他系统（如 Parquet）时很有帮助。

### 3. 如何获取 MCAP 文件进行练习？

Foxglove 提供了许多示例 MCAP 文件，可以直接下载：
```bash
# 下载一个包含传感器数据的 MCAP
wget https://github.com/foxglove/mcap/raw/main/tests/conformance/data/OneMessage/OneMessage.mcap

# 查看信息
mcap info OneMessage.mcap
mcap cat OneMessage.mcap
```
也可以在 Foxglove Studio 中直接拖放查看，直观地看到里面的图像、点云等。

## 第三部分：概念对比与第一周总结任务

| 特性 | rosbag v1 | rosbag v2 (默认SQLite) | MCAP |
|------|-----------|------------------------|------|
| 依赖 | ROS 1 环境 | ROS 2 环境 | 无 ROS 依赖 |
| 文件自描述 | 否 | 部分 | 完全 |
| 随机访问 | 需重建索引 | 支持（SQL） | 原生快速索引 |
| 多编码 | ROS msg 固定 | 主要 ROS msg | JSON/Protobuf/FlatBuffers/ROS等 |
| 生态系统 | 老旧、大规模存量数据 | 现在主流 | 未来趋势，跨平台 |
| 适合场景 | 遗留系统 | ROS 2 原生开发 | 云端处理、跨语言、长期存储 |

**第一周核心思想**：在不写任何代码的情况下，你要能流畅地用命令行完成以下任务：

1. 使用 `rosbag record` 录制一段自己发布的虚拟话题，然后 `rosbag info` 查看统计信息，`rosbag play` 回放。
2. 对一个 `.bag` 文件执行 `rosbag filter` 或 `ros2 bag convert` 生成子集或转换格式。
3. 使用 `mcap info` 快速了解一个 `.mcap` 文件的内容，用 `mcap cat` 提取部分消息，用 `mcap filter` 裁剪出感兴趣的时间段和通道。
4. 能在头脑中清晰说出：如果你想搭建一个处理从 ROS 机器人采集到的日志的云端服务，你会选择哪种格式作为中间存储？为什么？（答案通常是 MCAP）

当你对以上操作毫无障碍时，第一周的目标就达成了，也为下一周用 Python 库编程读写打下了扎实的基础。如果在命令使用中遇到具体报错，可以随时带着错误信息来追问。
