# 00：坐标系和时间戳

> 这是机器人数据中两个最容易让 Web 工程师困惑的概念。在 Web 里，坐标就是屏幕上的 x/y，时间就是服务器的一个时间戳。机器人的坐标和时间要复杂得多——这篇用你熟悉的场景讲清楚为什么。

## 1. 为什么需要一个"坐标系树"

### Web 里的坐标：一个原点就够

你在 Web 开发中处理坐标时，通常只有一个参照系：

```text
浏览器窗口坐标：(0,0) 在左上角
地图坐标：(0,0) 在某个固定经纬度
3D 场景坐标：(0,0,0) 在场景原点
```

所有元素都相对于同一个原点定位。简单明了。

### 机器人的坐标：每个部件都有自己的原点

一台人形机器人身上有十几个传感器，每个在自己的位置上测量数据：

```text
头部相机：拍到一张图，图中的杯子在相机前方 0.5m
  → "前方 0.5m" 是相对于谁的前方？是相机的，不是机器人的

左腕力传感器：测到 3N 向下的力
  → "向下" 是相对于谁的向下？是手腕的，不是地面的

底盘 IMU：测到绕 Z 轴旋转 0.5 rad/s
  → "Z 轴" 是哪个 Z 轴？IMU 的还是地面的？
```

如果每个传感器都用自己的坐标系，你就没法把数据组合起来用。你需要知道：**头部相机看到的杯子，在底盘坐标系下是什么位置？**

### TF 树：坐标系之间的关系图

TF（Transform）系统做的事情就是维护所有坐标系之间的变换关系。它是一棵树：

```text
地面（map）
  └── 里程计原点（odom）
        └── 机器人中心（base_link）
              ├── 躯干（torso_link）
              │     └── 头部（head_link）
              │           └── 头部相机（head_camera_link）
              ├── 左肩（shoulder_left_link）
              │     └── 左肘 → 左腕 → 左手
              └── 右肩（shoulder_right_link）
                    └── 右肘 → 右腕 → 右手
```

树上的每条边存的是一个变换关系："头部相机在头部的正前方 0.1m、上方 0.05m"。

当你想知道"头部相机看到的杯子在底盘坐标系下的位置"时，TF 沿着树路径逐级变换：

```text
head_camera_link → head_link → torso_link → base_link

每一步做一次坐标变换（平移 + 旋转）
最终得到：杯子在 base_link 坐标系下的 (x, y, z)
```

### Web 类比

如果你做过地图应用，可能处理过"瓦片坐标 ↔ 经纬度 ↔ 墨卡托投影"之间的转换。TF 树本质上就是这种坐标转换的自动化版本——你告诉它起点和终点，它自动沿着树算出变换。

```
地图应用:  像素坐标 (256, 128) → 瓦片坐标 → 经纬度 → 墨卡托
TF 系统:   head_camera 坐标 → head_link → torso → base_link
```

### 为什么用四元数而不是欧拉角

你可能见过 `orientation: (x, y, z, w)` 这种四元数表示，好奇为什么不直接用 `(roll, pitch, yaw)` 三个角度。

| 欧拉角 (roll, pitch, yaw) | 四元数 (x, y, z, w) |
|--------------------------|-------------------|
| 人类直觉好理解 | 计算更稳定 |
| **有万向锁问题**：当 pitch=90° 时，roll 和 yaw 会混在一起 | 没有万向锁 |
| 插值不平滑（旋转过渡会抖动） | 插值平滑 |
| 需要 3 个数 | 需要 4 个数 |

> **Web 类比**：四元数之于旋转，就像 homogeneous 坐标之于 3D 投影——多一个维度但消除了特殊情况。在 CSS 3D transforms 里你用过 `matrix3d()`，四元数本质上也是为了避免旋转的边界问题。

**你作为数据工程师需要知道的**：不要试图理解四元数的物理含义，把它当作一个 4 维向量处理就行。归一化时对 4 个维度一起算 mean/std。模型把它当 4 个输入特征用。需要可视化时再用库转换成欧拉角。

## 2. 为什么时间戳这么复杂

### Web 里的时间：一个时间戳就够

```python
# Web: 一个时间戳搞定
created_at = datetime.now()  # 2026-08-11 14:30:00
```

所有操作都在同一台服务器上，用同一个系统时钟。简单。

### 分布式系统里你已经遇到过的时钟问题

如果你做过微服务或多区域部署，可能遇到过：

```text
服务 A 的日志: 14:30:00.123 — 收到请求
服务 B 的日志: 14:30:00.118 — 处理完成

等等，B 比 A 还早？因为 A 和 B 的时钟没同步。
```

机器人的时间问题完全一样，只是更严重——因为传感器物理上分布在机器人各处，时钟源更多。

### 机器人里的四个时间

一条传感器消息至少涉及这些时间：

```text
① 硬件时间：传感器固件内部时钟记录的采样时刻
   → 最接近真实物理事件（如相机曝光）
   → 但和主机时钟可能不同步

② 驱动盖戳：驱动程序收到数据后写入 header.stamp 的时间
   → 可能用 ①（硬件时间），也可能用当前系统时间
   → 取决于驱动实现

③ log_time：bag 录制器收到消息的时间
   → 一定晚于 ②，因为消息要先经过 DDS 网络传输

④ 系统时间：操作系统的时钟
   → 如果用了 use_sim_time，这和真实时间脱钩
```

### 为什么 50ms 的时间差会出问题

想象你在做双臂抓取任务：

```text
头部相机（30fps）：每 33ms 拍一帧
左腕相机（30fps）：每 33ms 拍一帧

如果两个相机的时间戳差 50ms：
  头部相机帧 100: stamp = 10.000s  ← 机械臂在初始位置
  左腕相机帧 100: stamp = 10.050s  ← 机械臂已经移动了 50ms
  
在做最近邻匹配时：
  你以为这两帧是"同一时刻"的观测
  实际上机械臂在两帧之间已经移动了
  → 左腕相机拍到的手部位置和头部相机拍到的不匹配
  → 模型学到的是"错位"的观测
```

50ms 看起来很短，但机械臂以 1m/s 的速度运动时，50ms 就是 5cm 的位移。对于精确抓取来说，5cm 的错位足以导致失败。

### Web 类比

你在分布式系统里可能做过"请求链路追踪"（distributed tracing）。每跳一个服务加一个时间戳，最后按时间排序重建调用链。机器人的多传感器同步也是一样的——你需要把多个传感器在同一时刻的数据对齐，就像把多个微服务的日志按时间对齐一样。

```text
分布式追踪:    服务 A → 服务 B → 服务 C
               每跳的时间戳需要对齐才能重建调用链

多传感器同步:  相机 A + 相机 B + IMU + 关节
               每个传感器的时间戳需要对齐才能做融合
```

### 时间同步方案

| 方案 | 精度 | Web 类比 |
|------|------|---------|
| NTP | 1-50ms | NTP 同步服务器时钟 |
| chrony | 0.1-10ms | 更精确的 NTP 替代 |
| PTP (IEEE 1588) | < 1ms | 硬件辅助的精确时钟同步 |
| 硬件触发线 | < 0.001ms | 像数据库的两阶段提交——用硬件信号保证同时性 |

你的 Orbbec 数据用的是"Orbbec SDK 多设备同步"，本质是硬件触发方案，同步精度 < 1ms（manifest 里 mean=126µs）。这是最好的方案。

## 3. 把两个概念合起来：frame_id + stamp 的组合含义

每条传感器消息都有这两个字段：

```text
header.stamp = 1780625604850000000 (ns)   ← 这是"什么时候"测的
header.frame_id = "head_camera_link"       ← 这是"在哪里"测的
```

它们组合在一起表达的含义是：

> "在时间戳 1780625604.85s 这个时刻，在 head_camera_link 这个坐标系位置上，测量到了这组数据。"

两个都必须正确：
- 时间错了 → 多传感器数据对不齐
- 坐标系错了 → 数据的空间含义错了

你在数据工程中的核心任务之一就是：确保每条数据的 `stamp` 和 `frame_id` 都是可信的、可追溯的、并且在处理过程中不被意外篡改。

## 4. 本篇要点

- 机器人不是一个坐标系，而是十几个——TF 树维护它们之间的变换关系，类似地图应用的坐标转换链。
- 四元数是用来表示旋转的 4 维向量，你不需要理解它的物理含义，当作一个特征向量处理就行。
- 一条消息至少有 4 个时间（硬件、驱动盖戳、log_time、系统时间），它们的差值决定了数据质量。
- 50ms 的时间误差对精确操作来说就是 5cm 的位置错位——足以导致任务失败。
- frame_id + stamp 的组合含义是"什么时候、在哪里测的"——两者都必须正确。
