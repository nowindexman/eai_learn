# 00：机器人数据是什么

> 你做过 Web 开发，知道 HTTP 请求、数据库、消息队列、日志系统。机器人数据的采集链路和这些有相似之处，但有关键差异。本篇用你已知的概念建立对"传感器→消息→话题→bag"的直觉。

## 1. 一条传感器数据是怎么产生的

想象你在做一个 Web 应用，用户点击按钮，前端发了一个 POST 请求：

```text
用户点击 → 浏览器 → HTTP 请求 → 服务器 → 数据库
```

机器人的数据产生链路是类似的：

```text
物理事件（相机曝光） → 传感器固件 → 驱动程序 → ROS 消息 → 话题 → bag 录制
         ↑                ↑            ↑          ↑        ↑
      硬件时钟盖戳     USB/网络传输   解码+封装   发布      订阅+写文件
```

**关键区别**：Web 请求是人触发的、离散的、一次一个。传感器数据是机器触发的、连续的、每秒几十到几百条。

一台机器人可能同时运行：
- 2 个相机 × 30fps = 每秒 60 条图像消息
- 1 个 IMU × 200fps = 每秒 200 条姿态消息
- 14 个关节状态 × 50fps = 每秒 50 条关节消息
- 总计：每秒约 310 条消息，持续不断

这就是为什么机器人数据需要专门的采集和存储格式——它不是"偶尔来一条请求"，而是持续高速的数据流。

## 2. ROS 消息 ≈ API 的 JSON Payload

你在 Web 里习惯的数据格式是 JSON：

```json
{
  "user_id": 123,
  "action": "click",
  "timestamp": "2026-08-11T10:00:00Z"
}
```

机器人里的等价物是 ROS 消息。一个关节状态消息长这样（概念上的字段）：

```text
header:
  stamp: 1780625604.850000000    ← 这条数据是什么时候产生的
  frame_id: "base_link"          ← 这个数据在哪个坐标系下
name: ["shoulder_left", "elbow_left", "wrist_left"]
position: [0.12, -0.87, 0.45]    ← 三个关节的当前角度（弧度）
velocity: [0.01, -0.03, 0.02]
effort: [0.5, 0.3, 0.1]
```

**和 JSON 的相似处**：都是结构化的、有字段名和值。
**和 JSON 的关键区别**：

| 维度 | Web JSON | ROS 消息 |
|------|---------|---------|
| 类型系统 | 动态（运行时解析） | 强类型（预定义 schema） |
| 序列化 | 文本 | 二进制（更紧凑、更快） |
| 时间戳 | 可选 | 几乎每条都有 |
| 坐标系 | 无 | 有（frame_id） |
| 数组 | 任意长度 | 有固定长度和语义（如 36 个数 = 6×6 协方差矩阵） |

> **为什么不用 JSON？** 因为 JSON 是文本格式，一条 1280×720 的图像消息如果转成 JSON 会是几百万个数字的文本——体积是二进制的 4-8 倍，解析速度慢 10-100 倍。机器人的数据量级决定了必须用二进制序列化。

## 3. 话题 ≈ 消息队列的 Topic

你在 Web 里可能用过 Kafka / RabbitMQ / Redis Pub-Sub。它们的核心概念是：

```text
生产者 → 发消息到 Topic → 消费者订阅 Topic
```

ROS 的话题系统几乎一样：

```text
传感器驱动（发布者） → 发消息到 /robot/joint_states → 你的程序（订阅者）
                                            ↘ bag 录制器（也是订阅者）
```

| 概念 | Kafka / RabbitMQ | ROS Topic |
|------|-----------------|-----------|
| 消息通道 | Topic / Queue | Topic |
| 生产者 | Producer | Publisher |
| 消费者 | Consumer | Subscriber |
| 消息格式 | Avro / Protobuf | ROS msg / CDR |
| 持久化 | 存到磁盘 | 默认不存（bag 是"录制"才存） |
| 发现机制 | 需要配置 broker | 自动发现（DDS） |
| 可靠性 | ACK / 重试 | QoS 策略 |

**最重要的区别**：Kafka 的消息默认持久化（存在 broker 上），ROS 的消息默认**不持久化**——消息发出去就被消费了，不留痕迹。`ros2 bag record` 相当于在消息流上挂了一个"录制订阅者"，把经过的消息写进文件。

> 所以 bag 文件本质上是一个**消息流的录制文件**，就像你用 `tcpdump` 录制网络流量一样。

## 4. bag 文件 ≈ 数据库的 Binlog / 日志归档

| Web 类比 | bag 文件 |
|---------|---------|
| MySQL binlog | 按时间顺序记录所有变更 |
| ELK 中的日志索引 | 可按时间范围查询和回放 |
| Kafka 的 segment 文件 | 分段存储、可重放 |

bag 的核心特征：

```text
1. 追加写入：录制时持续追加，不修改历史
2. 时间索引：每条消息都有时间戳，可按时间回放
3. 多流混合：一个 bag 里可以有几十个话题的消息交织在一起
4. 可重放：rosbag play 把消息重新发回 ROS 网络，就像"时光倒流"
```

**为什么不能直接用数据库存？** 因为传感器数据是高速流式写入（每秒几百条），传统数据库的写入延迟太高。bag 用的是专门优化的顺序追加格式，写入速度远高于数据库。

## 5. 你仓库里的数据对应关系

```text
你仓库里的东西              Web 类比
──────────────              ────────
publish_demo_ros2.py      ← 一个不停发 HTTP 请求的压测脚本
rosbag2_2026_08_07_*      ← 一次压测的录制文件（access log）
zyw_mcap_0.mcap           ← 同一份录制，换了个存储格式
数据采集样本/*.bag         ← 生产环境录制的真实流量
manifest.json             ← 这次录制的元信息（Nginx access log 的 header）
```

## 6. 串联起来：完整的数据生命周期

```text
物理世界                    Web 世界类比
────────                    ────────────
机器人运动
  ↓
传感器采样（相机/IMU/关节）   ← 用户在浏览器里的操作
  ↓
驱动程序打包成 ROS 消息      ← 前端把操作封装成 HTTP 请求
  ↓
发布到话题                   ← 发送到 API 端点
  ↓
ros2 bag record 录制        ← Nginx access log 记录请求
  ↓
bag / MCAP 文件             ← 日志文件
  ↓
你的 Python 脚本读取         ← 日志分析脚本（ELK / Splunk）
  ↓
提取、清洗、同步             ← ETL pipeline
  ↓
训练数据集（LeRobot/HDF5）   ← 数据仓库中的分析表
  ↓
模型训练                    ← BI 报表 / ML 训练
```

每一步都对应你熟悉的 Web 概念。后续文档里的每个新术语，你都可以回来查这张映射表。

## 7. 本篇要点

- 传感器数据是**高速持续的数据流**，不是离散请求——这决定了存储格式和处理方式。
- ROS 消息 ≈ 强类型的二进制 JSON，话题 ≈ Pub-Sub 的 Topic。
- bag 文件 ≈ 消息流录制文件，像数据库 binlog 或网络抓包。
- 你后续做的所有"读取 bag → 清洗 → 转格式"的工作，本质和"读日志 → ETL → 入仓库"完全一样。
