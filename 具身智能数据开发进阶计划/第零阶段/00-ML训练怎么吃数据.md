# 00：ML 训练怎么吃数据

> 你做过 Web 开发，知道 API 的"一条请求一条响应"。但 ML 训练完全不是这个模式。本篇用你能理解的方式讲清楚：模型训练时数据是怎么进入 GPU 的，为什么需要 batch、为什么需要时间窗口、为什么不能直接拿 bag 里的单条消息去训练。

## 1. Web 处理 vs ML 训练：根本差异

你在 Web 里习惯了这样的处理模式：

```text
用户请求 → 服务器处理 → 返回响应

特征：
- 一次处理一条
- 每条独立
- 实时响应（< 1秒）
- 处理完就忘（无状态）
```

ML 训练是这样的：

```text
全部数据 → 切成 batch → 逐 batch 送入 GPU → 算 loss → 更新权重
                                                        ↓
                                              重复几十到几百轮（epoch）

特征：
- 一次处理一批（32-256 条）
- 同一个 batch 内的数据互相影响梯度
- 每轮要遍历全部数据
- 同一份数据要看几十到几百遍
```

**核心区别**：Web 是"来一条处理一条"，ML 是"把所有数据看几百遍，每遍都微调模型"。

## 2. 为什么不能一条一条喂

假设你有 10000 帧训练数据，每帧包含关节状态和图像。

**方案 A：一条一条喂（错误）**

```text
第 1 帧 → GPU → 算 loss → 更新权重
第 2 帧 → GPU → 算 loss → 更新权重
...
第 10000 帧 → GPU → 算 loss → 更新权重
```

问题：
1. **GPU 利用率极低**：GPU 的设计是并行计算。只送一条数据进去，就像用一个 32 车道的高速公路跑一辆车。
2. **梯度方向不稳定**：每条数据单独更新权重，方向会在各帧之间剧烈震荡。就像蒙着眼走路，每步随机方向。
3. **太慢**：10000 帧逐条处理，GPU 启动开销远大于计算时间。

**方案 B：组成 batch（正确）**

```text
batch 1（32 帧） → GPU → 算平均 loss → 更新权重
batch 2（32 帧） → GPU → 算平均 loss → 更新权重
...
batch 313（最后 16 帧） → GPU → 算平均 loss → 更新权重
= 1 个 epoch（看完一遍全部数据）
```

batch 内的 32 条数据一起算 loss 取平均，梯度方向更稳定。GPU 并行计算 32 条数据的效率和算 1 条几乎一样快。

> **Web 类比**：就像数据库的批量插入。你不会 `INSERT INTO ... VALUES (1)` 然后 `INSERT INTO ... VALUES (2)` 一条一条插，而是 `INSERT INTO ... VALUES (1), (2), ..., (32)` 批量插。ML 的 batch 就是这个道理。

## 3. DataLoader：训练数据的"分页加载器"

PyTorch 的 `DataLoader` 做的事情，和你在 Web 里做的数据库分页查询很像：

```python
# Web 思路：分页查询数据库
for page in range(total_pages):
    rows = db.query("SELECT * FROM data LIMIT 32 OFFSET ?", page * 32)
    process(rows)

# ML 思路：DataLoader 分批加载数据
for batch in dataloader:
    loss = model(batch)        # 送入 GPU
    loss.backward()            # 算梯度
    optimizer.step()           # 更新权重
```

DataLoader 的职责：

| DataLoader 做的事 | Web 类比 |
|-----------------|---------|
| 把数据切成 batch | 分页查询的 LIMIT/OFFSET |
| 打乱顺序（shuffle） | 避免相同类别的数据连续出现导致偏差 |
| 多进程并行加载 | 连接池并发查询 |
| 预取下一批（prefetch） | CDN 预加载下一页资源 |
| 把数据转成 GPU tensor | 序列化成 JSON 响应 |

**关键**：DataLoader 是模型和数据集之间的"中间件"。你的数据集只需要提供"第 N 条数据是什么"（`__getitem__`），DataLoader 负责组装 batch、打乱、预取。

```python
# 你的数据集只需要实现这两个方法
class MyDataset:
    def __len__(self):           # 总共有多少条
        return 10000

    def __getitem__(self, idx):  # 第 idx 条是什么
        return {
            "image": load_image(idx),     # (C, H, W) tensor
            "state": load_state(idx),      # (state_dim,) tensor
            "action": load_action(idx),    # (action_dim,) tensor
        }

# DataLoader 负责组装
dataloader = DataLoader(
    MyDataset(),
    batch_size=32,     # 每批 32 条
    shuffle=True,      # 打乱顺序
    num_workers=4,     # 4 个进程并行加载
)
```

## 4. 为什么不能直接拿 bag 里的消息训练

bag 里的一条消息是这样的：

```python
# bag 里的一条 JointState 消息
{
    "header": {"stamp": ..., "frame_id": "base_link"},
    "name": ["shoulder_left", "elbow_left", ...],
    "position": [0.12, -0.87, ...],
    "velocity": [0.01, -0.03, ...],
}
```

你不能直接把它喂给模型，因为：

**问题 1：维度不统一**

bag 里的消息是 Python 对象或字典，维度和类型不固定。模型需要的是 `torch.Tensor`——固定维度、固定 dtype 的多维数组。

```text
bag 消息:  position = [0.12, -0.87, 0.45, ...]  ← Python list
模型需要:  torch.Tensor([0.12, -0.87, 0.45, ...], dtype=float32)  ← 固定类型
```

**问题 2：时间维度缺失**

bag 里的每条消息是**一个时间点**的快照。但模型需要的是**一个时间窗口**：

```text
bag 里的数据（逐帧）:
  帧 0: state=[...], action=[...]
  帧 1: state=[...], action=[...]
  帧 2: state=[...], action=[...]

模型需要的数据（窗口化）:
  样本 0:
    observation = {过去 3 帧的图像和状态}
    action = {未来 10 步的动作}

  样本 1:
    observation = {帧 1-3 的图像和状态}
    action = {帧 4-13 的动作}
```

这就是为什么你需要一个转换步骤——把逐帧的 bag 数据，切成带时间窗口的训练样本。这个转换就是你第一阶段要学的核心技能。

**问题 3：数值范围不统一**

不同关节的角度范围差异很大：

```text
shoulder_pan: -1.57 ~ 1.57    （范围 3.14）
gripper:       0.00 ~ 0.05    （范围 0.05）
```

如果直接把原始值送入模型，模型会"关注"大数值的维度、忽略小数值的维度。需要归一化（前面对话中详细讲过）。

**问题 4：数据类型和格式**

bag 的序列化格式（ROS 1 序列化或 CDR）不是 PyTorch 能直接读的格式。需要先反序列化成 Python 对象，再转成 Tensor。中间还要经过时间同步、字段提取、单位确认等步骤。

## 5. 完整的数据消费链路

```text
bag 文件（原始录制）
  │
  │  读取 + 反序列化（rosbags 库）
  ↓
Python 消息对象（逐帧）
  │
  │  时间对齐 + 字段提取 + 质量检查
  ↓
结构化数据表（Parquet / DataFrame）
  │
  │  归一化统计 + 格式转换
  ↓
训练数据集（LeRobot / HDF5 / Zarr）
  │
  │  DataLoader 按需加载 + 窗口切分 + batch 组装
  ↓
GPU Tensor（batch_size × channels × height × width）
  │
  │  模型前向传播 → 算 loss → 反向传播 → 更新权重
  ↓
训练后的模型权重
```

你在整个链路中的角色是前四层（bag → 消息对象 → 数据表 → 训练数据集）。最后两层（DataLoader → GPU）是训练代码做的，但你需要理解它们的接口要求，才能产出正确的数据集。

## 6. 为什么有这么多训练数据格式

现在你应该能理解为什么不能统一用一种格式了：

```text
训练的需求                     格式选择
──────                         ────────
"我要快速随机访问第 N 帧"      → HDF5（索引好）或 LeRobot（Parquet 索引好）
"数据集 500GB，不能全下到本地"  → LeRobot（HF Hub 流式）或 Zarr（分块读取）
"我的图像必须无损"             → HDF5（gzip 无损）而非 MP4（有损）
"我要和 Open X-Embodiment 兼容" → RLDS（它的生态要求）
"我要 Diffusion Policy 直接跑"  → Zarr（它的代码只读 Zarr）
```

每种格式都是在不同维度上做权衡。没有"最好的格式"，只有"最适合你当前需求的格式"。

## 7. 用一个比喻总结

把整个流程想象成一个餐厅：

```text
食材供应商（传感器）       → 提供原始食材（原始消息）
  ↓
进货检查（inspect）         → 检查食材新鲜度（帧率、时间、类型）
  ↓
清洗切配（清洗同步）        → 洗菜、切菜、按菜谱分组（时间对齐、字段提取）
  ↓
半成品（训练数据集）        → 准备好的配菜盒（LeRobot/HDF5）
  ↓
厨师按菜单取用（DataLoader） → 一次取一批配菜做菜（batch 加载）
  ↓
出品（模型训练）            → 一道菜（一次权重更新）
```

你是负责"进货到半成品"的供应链经理。厨师（训练代码）只需要打开配菜盒就能开始做菜。如果配菜盒的规格不对（维度错了、没归一化、时间没对齐），厨师做出来的菜就不好（模型效果差）。

## 8. 本篇要点

- ML 训练不是"一条一条处理"，而是"一批一批喂给 GPU"——和数据库批量插入同理。
- DataLoader 是数据和 GPU 之间的中间件，负责切 batch、打乱、预取。
- bag 里的单条消息不能直接训练——需要经过反序列化、时间对齐、归一化、窗口化、格式转换。
- 多种训练格式存在的根本原因是不同训练场景的需求不同（随机访问 vs 流式 vs 无损 vs 兼容性）。
- 你的角色是供应链：产出规格正确的"配菜盒"，让训练代码（厨师）直接能用。
