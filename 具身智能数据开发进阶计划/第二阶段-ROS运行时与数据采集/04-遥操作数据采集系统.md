# 04：遥操作数据采集系统

> 遥操作（Teleoperation）是获取高质量模仿学习数据的主要方式：人类操作者直接控制机器人完成任务，全程记录机器人的状态、动作和传感器观测。理解这个流程，你才能设计数据采集的质量监控方案，并在数据出现问题时定位是操作者、设备还是系统的原因。

## 1. 为什么需要遥操作

模仿学习（Imitation Learning）需要人类示范数据。这些数据的质量直接决定模型上限：

```text
强化学习：      机器人自己试错 → 数据量大但质量不可控
仿真数据：      合成数据 → 成本低但有 sim-to-real gap
遥操作：        人类示教 → 质量最高但成本也最高
```

遥操作产生的数据是**最接近训练需求的**——它天然就是 (observation, action) 对，因为人类的控制命令就是 action，机器人状态就是 observation。

### 1.1 三条路线详细对比

上面三行话浓缩了具身智能数据获取的三条根本不同的技术路线。理解它们各自的数据特性、成本结构和工程挑战，你才能理解为什么遥操作在工业级采集中不可替代。

#### 路线一：强化学习（机器人自主试错）

**核心思想**：给机器人定义一个奖励函数（reward），让它自己在环境中反复尝试，通过试错找到能获得高奖励的动作策略。

```text
┌──────────────┐    动作 a_t    ┌──────────────┐
│   Robot/Env  │ ◄──────────── │   Policy π   │
│              │               │  (神经网络)   │
│  状态 s_t    │ ────────────► │              │
│  奖励 r_t    │   状态+奖励    │              │
└──────────────┘               └──────────────┘

循环数百万次，Policy 逐渐学会"怎么做能拿高分"
```

**数据特性**：

| 维度 | 说明 |
|------|------|
| 数据量 | 极大——一次训练可能产生数百万条 transition（s, a, r, s'） |
| 数据质量 | 不可控——前期全是随机探索，大量"垃圾"轨迹 |
| 数据格式 | RL 内部的 replay buffer，不是 (obs, action) 示教对 |
| 标注成本 | 不需要人工标注，但需要精心设计 reward |

**致命短板**：

1. **Reward 设计极难**：对于"把杯子端起来不洒水"这种任务，你很难写出一个数学公式精确衡量"成功且优雅"。Reward hacking（机器人找到漏洞刷分但不真正解决问题）是头号顽疾。
2. **样本效率极低**：Sim-to-real 需要海量迭代。一只机器狗学会走路，仿真环境里可能摔了上百万次。
3. **真实世界试错代价高昂**：在真机上跑 RL，机器人可能把自己撞坏。工业场景几乎不会在真机上做 RL 探索。
4. **数据无法直接复用**：RL 产生的 transition 数据绑定了特定 policy 和环境，换个任务基本作废。

**数据工程视角**：RL 数据 pipeline 的核心挑战是 replay buffer 管理——如何在百万级 transition 中高效采样、管理优先级（PER）、处理分布漂移。但这属于算法工程师的领域，数据工程师主要做离线日志收集和训练监控。

#### 路线二：仿真数据（合成数据）

**核心思想**：在物理仿真器（Isaac Sim、MuJoCo、PyBullet）中构建虚拟世界，用脚本或程序化策略生成大量演示数据，或直接在仿真中跑 RL。

```text
Simulator (Isaac Sim / MuJoCo)
  ├── 虚拟场景：桌子、物体、光照（程序化随机化）
  ├── 虚拟传感器：相机渲染、IMU 模拟、关节编码器
  ├── 虚拟机器人：URDF/MJCF 模型，物理引擎驱动
  └── 数据生成：
        ├── 脚本策略（已知最优路径，自动批量生成）
        ├── 仿真内 RL（快速迭代，不担心撞坏）
        └── Domain Randomization（随机化纹理/光照/物理参数）
              → 输出：合成 (obs, action) 对，格式与真实数据一致
```

**数据特性**：

| 维度 | 说明 |
|------|------|
| 数据量 | 几乎无限——GPU 集群可以 7×24 生成 |
| 数据质量 | 完美——传感器零噪声、时间完美同步、标签自动获取 |
| 数据格式 | 可直接输出为与真实采集相同的格式（HDF5/LeRobot/bag） |
| 标注成本 | 零——仿真器知道一切物体的精确位姿，标签"免费" |

**致命短板——Sim-to-Real Gap**：

1. **物理简化**：仿真器的摩擦、接触、变形都是近似。真实世界的摩擦系数会变、物体表面会粘、绳子会缠绕——这些在仿真中很难精确建模。
2. **视觉域差异**：仿真渲染的图像和真实相机的图像在光照、噪声、景深上有差距。仿真训练的策略迁移到真机时，策略看到的图像分布变了，性能会下降。
3. **Domain Randomization 的代价**：为了让策略对仿真-真实差异"鲁棒"，常用做法是大量随机化仿真参数（光照角度、物体颜色、摩擦系数……）。但这会让训练难度暴增，策略要覆盖的分布太广。
4. **复杂任务的仿真本身就很贵**：柔性物体（布料、绳索）、流体、可变形物体的仿真计算成本极高，且精度更差。

**数据工程视角**：仿真数据的 pipeline 核心是**规模化生成 + 自动质检**。你需要管理：
- 批量场景生成（不同物体组合、位姿、光照）
- 并行渲染调度（多 GPU/多机）
- 合成数据的自动标注和格式转换
- Sim-to-real 的数据配比策略（多少仿真 + 多少真实数据混合训练）

#### 路线三：遥操作（人类示教）

**核心思想**：人类操作者通过遥操作设备实时控制机器人完成任务，系统同步记录机器人的全部状态和传感器观测。人类的行为就是"标准答案"。

```text
人类操作者
  │
  ├── 通过设备控制 ──► Leader臂 / VR手柄 / Space Mouse
  │                        │
  │                        ▼
  │                   控制器（映射 + 安全限制）
  │                        │
  │                        ▼
  │                   机器人执行动作
  │                        │
  │            ┌───────────┼───────────┐
  │            ▼           ▼           ▼
  │        相机图像    关节状态    力/触觉
  │            │           │           │
  │            └───────────┼───────────┘
  │                        ▼
  │              全程录制 → (observation, action) 对
  │
  └── 人类决策就是 action 标签 → 数据质量取决于操作者水平
```

**数据特性**：

| 维度 | 说明 |
|------|------|
| 数据量 | 小——一个 episode 几十秒到几分钟，一天采集几十到上百个 |
| 数据质量 | 最高——人类天然产生平滑、合理、目标导向的动作 |
| 数据格式 | 天然就是训练需要的 (obs, action) 对，转换最简单 |
| 标注成本 | 每条数据都需要人工操作，人力成本是主要开销 |

**为什么不可替代**：

1. **真实分布**：数据来自真实传感器、真实物理、真实环境。没有 sim-to-real gap。
2. **隐式知识传递**：人类操作中包含大量难以显式编码的技能——力的把控、对物体滑动的预判、异常恢复策略。这些是脚本和 RL 无法廉价获得的。
3. **直接可用**：action 就是人的控制命令，不需要额外推断"正确动作应该是什么"。

**核心代价**：

1. **贵且慢**：熟练操作者每小时可能只采集 10-20 个有效 episode。如果任务复杂（如精密装配），有效数据产出更低。
2. **操作者差异**：不同人的操作风格（速度、路径偏好、力的轻重）不同，数据集会引入操作者偏差。需要多操作者混合 + manifest 记录操作者 ID。
3. **规模天花板**：人类采集的 throughput 远低于仿真生成。业界顶级数据集（如 Open X-Embodiment）也就几百万条轨迹，而仿真可以轻松过亿。

### 1.2 三条路线的工程决策矩阵

```text
                    RL 自主试错        仿真合成          遥操作示教
                   ─────────────    ─────────────    ─────────────
数据产量            极大              几乎无限          小（人工瓶颈）
数据质量            不可控            完美但失真        最高（真实分布）
单条成本            中（算力）        极低（GPU）       极高（人力+设备）
标注成本            无需标注          自动获取          操作即标注
数据格式转换        复杂（非示教格式） 简单（可对齐格式） 最简单（天然对齐）
Sim-to-Real         不适用            有差距            无差距
适用阶段            算法探索          大规模预训练      精调/对齐/评测
```

### 1.3 工业界实际做法：三路混合

实际项目几乎不会只用一条路线，而是组合使用：

```text
阶段 1：仿真预训练
  └── 用仿真数据（脚本 + 仿真RL）训练基础策略
      → 快速验证可行性，低成本获得初始能力

阶段 2：遥操作精调
  └── 用小批量高质量遥操作数据做模仿学习 / 微调
      → 把策略从仿真域拉回真实域，消除 sim-to-real gap

阶段 3：真机自主 + 人工修正
  └── 策略自主运行，失败时人类介入修正（DAgger / HFIL）
      → 持续收集"难样本"，迭代提升策略鲁棒性

数据配比经验：
  仿真 : 遥操作 : 自主 ≈ 70% : 25% : 5%（视任务复杂度调整）
```

> **作为数据工程师的关键认知**：遥操作数据虽然量小，但它是整个数据集中**价值密度最高**的部分。你的 manifest 设计、质量监控、episode 管理、审核流程——这些工程化的精细程度，直接决定了这 25% 的高价值数据中有多少是真正可用的。这也是为什么本章花大量篇幅讲遥操作采集系统的原因。

## 2. 遥操作的硬件方案

### 2.1 Leader-Follower 双臂（最常见于操作任务）

两台相同的机械臂：leader 臂被人手驱动（不带动电机），follower 臂实时跟随 leader 的关节角度。

```text
人手 → leader 臂（关节角度传感器）→ 控制器 → follower 臂（电机驱动）

action = leader 关节角度（人的操作意图）
observation = follower 的实际关节状态 + 相机图像
```

优点：action 和 observation 都来自同一型号设备，语义一致。
缺点：需要两套硬件，成本高。

### 2.2 VR 手柄/头显（适合移动操作和导航）

使用 Meta Quest、Apple Vision Pro 等 VR 设备的控制器跟踪手部位姿，映射到机器人末端执行器。

```text
VR 控制器（6-DOF 位姿）→ IK 求解 → 机器人关节命令

action = 末端位姿或关节命令
observation = 相机图像 + 机器人状态
```

优点：不需要第二套机械臂，VR 设备相对便宜。
缺点：有 IK 映射误差，VR 跟踪精度不如机械臂编码器。

### 2.3 Space Mouse / 3D Mouse

6 自由度输入设备，常用于遥控底盘或简单操作：

```text
Space Mouse（6 轴位移）→ 速度命令（Twist）

action = cmd_vel（线速度 + 角速度）
observation = 相机图像 + 里程计
```

### 2.4 其他方案

| 方案 | 原理 | 典型用途 |
|------|------|---------|
| 键盘/手柄 | 离散命令 | 简单导航、标注辅助 |
| 力反馈手套 | 手指关节角度 | 灵巧手操作 |
| 动捕服 | 全身关节角度 | 人形机器人全身示教 |
| 屏幕拖拽 | 直接指定目标位姿 | 简单 pick-and-place |

## 3. 数据采集流程

一个完整的遥操作采集 session：

```text
1. 环境准备
   ├── 确认相机/IMU 驱动正常，时间已同步
   ├── 确认 TF 树完整，frame_id 正确
   ├── 确认 QoS 配置，不会丢帧
   └── 启动录制器

2. 操作者示教
   ├── 操作者通过遥操作设备控制机器人
   ├── 系统实时记录所有话题
   ├── 质量监控：帧率、延迟、关节限位
   └── 每个 episode 开始/结束由操作者或自动逻辑标记

3. 数据收尾
   ├── 正常停止录制（SIGINT）
   ├── 计算 bag 校验和
   ├── 生成 manifest（含 episode 分段、任务标签、设备信息）
   └── 可选：实时预览检查

4. 人工审核
   ├── 回放检查图像、动作、时间对齐
   ├── 标记 episode 成功/失败
   └── 记录审核结论
```

## 5. Episode 管理

### 什么是 episode

一个 episode 是机器人执行一次完整任务的连续数据。它有明确的开始和结束：

```text
Episode = {
    开始：机器人到达初始位姿，操作者发出"开始"信号
    内容：持续的任务执行（抓取、移动、放置等）
    结束：任务完成、操作者发出"停止"、或异常中断
}
```

### Episode 边界标记

```python
# 方式 1：使用专门的开始/停止话题
# 操作者按按钮 → 发布 std_msgs/Bool 到 /episode/start
# 再次按按钮 → 发布到 /episode/stop

# 方式 2：使用任务状态话题
# publish_demo.py 中的 /robot/task_state 就是类似的机制
# task_state 从 IDLE 变为 WALK_TO → episode 开始
# task_state 回到 IDLE → episode 结束

# 方式 3：在 manifest 中记录时间戳
{
    "episode_index": 0,
    "start_timestamp_ns": 1780625604850000000,
    "end_timestamp_ns": 1780625674530000000,
    "task": "pick_box",
    "success": true
}
```

### 多步骤任务的 Episode 拆分

你的 manifest 中 `task_id: "scene-box-transfer"` 和 `step_id: "pick-box"` 暗示这是一个多步骤任务：

```text
完整任务：box-transfer（搬箱子）
  ├── step 1: pick-box（拿起箱子）  ← 你当前的 take-003
  ├── step 2: carry-box（搬运箱子）
  └── step 3: place-box（放下箱子）

训练时策略：
  方案 A：每个 step 一个 episode，分别训练
  方案 B：整个 task 作为一个 episode，训练完整链路
  方案 C：两种都做，用不同的模型分别处理
```

## 6. 采集质量监控

### 实时监控指标

在采集过程中应该实时监控的指标：

| 指标 | 检查方式 | 异常处理 |
|------|---------|---------|
| 帧率 | 各话题的 hz 是否达标 | 低于阈值时报警 |
| 时间同步 | 多传感器帧时间偏差 | 超阈值时暂停采集 |
| 关节限位 | 关节角度是否超限 | 触发安全停止 |
| 网络状态 | DDS 延迟和丢包率 | 网络抖动时降帧率 |
| 磁盘空间 | 剩余空间 | 不足时停止采集 |

### 离线质量检查

采集后（你的前置计划学过的部分）：

```python
@dataclass(frozen=True)
class EpisodeQualityReport:
    """单个 episode 的质量报告。"""
    episode_id: str
    duration_seconds: float

    # 帧完整性
    expected_frames: int       # 根据 FPS 和时长计算
    actual_frames: int         # 实际录到的帧数
    frame_completeness: float  # actual / expected

    # 时间质量
    has_negative_jumps: bool
    max_frame_gap_ms: float    # 最大帧间隔

    # 多传感器对齐
    sync_mean_delta_us: float  # 多相机平均偏差
    sync_max_delta_us: float

    # 语义质量（人工审核后填写）
    success: bool | None       # 任务是否成功
    issues: list[str]          # 发现的问题列表

    @property
    def quality_grade(self) -> str:
        if self.frame_completeness < 0.9:
            return "reject"
        if self.sync_max_delta_us > 5000:
            return "warning"
        if self.success is False:
            return "reject"
        return "accept"
```

### 操作者一致性

不同操作者（或同一操作者在不同时段）的数据可能存在风格差异：

| 差异来源 | 对训练的影响 | 应对策略 |
|---------|------------|---------|
| 执行速度不同 | action 分布变化 | 在 manifest 中记录操作者 ID |
| 路径偏好不同 | 观测分布变化 | 多操作者混合训练 |
| 成功率不同 | 数据集偏差 | 按 success 筛选或加权 |

## 7. 采集系统的数据工程职责

作为数据工程师，你在采集系统中的职责不是操作机器人，而是：

1. **采集前**：配置录制话题、QoS、时间同步、TF 检查。
2. **采集中**：实时监控帧率、延迟、磁盘、同步质量。
3. **采集后**：生成 manifest、校验和、质量报告、episode 分段。
4. **入库前**：审核、标记、版本化、上传到数据湖。

```python
def post_collection_pipeline(
    bag_path: Path,
    manifest_path: Path,
    output_dir: Path,
) -> dict:
    """采集后处理流水线。

    返回处理结果摘要，用于数据入库决策。
    """
    result = {
        "input_bag": str(bag_path),
        "bag_sha256": compute_sha256(bag_path),
        "episodes": [],
        "quality_summary": {},
    }

    # 1. 从 manifest 提取 episode 信息
    manifest = json.loads(manifest_path.read_text())
    task = f"{manifest['task_id']}_{manifest['step_id']}"

    # 2. 检查帧完整性
    frame_report = check_frame_completeness(bag_path, manifest)

    # 3. 检查时间同步质量
    sync_report = extract_sync_quality(manifest)

    # 4. 生成质量等级
    quality = EpisodeQualityReport(
        episode_id=manifest["session_id"],
        duration_seconds=manifest["duration_seconds"],
        expected_frames=frame_report["expected"],
        actual_frames=frame_report["actual"],
        frame_completeness=frame_report["completeness"],
        has_negative_jumps=frame_report["has_negative_jumps"],
        max_frame_gap_ms=frame_report["max_gap_ms"],
        sync_mean_delta_us=sync_report["mean_delta_us"],
        sync_max_delta_us=sync_report["max_delta_us"],
        success=manifest.get("review_decision") == "accepted",
        issues=frame_report["issues"],
    )

    result["episodes"].append(quality.__dict__)
    result["quality_summary"]["grade"] = quality.quality_grade

    return result
```
