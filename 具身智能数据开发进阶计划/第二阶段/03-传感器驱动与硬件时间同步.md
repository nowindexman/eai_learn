# 03：传感器驱动与硬件时间同步

> 你在前置计划中学过 `header.stamp` 和 `log_time` 的区别。但 `header.stamp` 本身的质量取决于整个时间链路：硬件时钟 → 驱动盖戳 → ROS 消息 → bag 记录。理解这条链路，你才能判断时间戳到底有多可信。

## 1. 传感器数据的时间链路

一条传感器消息从物理世界到 bag 文件，经过的每一环都会引入时间误差：

```text
物理事件（如：相机曝光）
  │ ① 硬件时钟盖戳：曝光发生时，传感器固件用内部时钟打时间戳
  ↓
传感器固件
  │ ② 传输延迟：USB / 以太网 / 串口传输到主机
  ↓
驱动程序
  │ ③ 驱动盖戳：驱动收到数据后的时间处理策略
  ↓    - 策略 A：使用传感器硬件时间（更接近真实曝光时刻）
  ↓    - 策略 B：使用主机收到时的系统时间（更简单，但有传输延迟）
  ↓    - 策略 C：使用 ROS 时间（now()）
  ↓
ROS 消息（header.stamp）
  │ ④ DDS 发布：消息通过 DDS 发布到话题
  ↓
ros2 bag record
  │ ⑤ 记录时间（log_time）：录制器收到消息的时间
  ↓
bag 文件
```

**关键区分**：

| 时间 | 位置 | 代表什么 |
|------|------|---------|
| 硬件时间 | 步骤 ① | 最接近真实物理事件，但需要时钟同步才能与主机对齐 |
| 驱动盖戳 | 步骤 ③ | header.stamp 的实际来源，取决于驱动实现 |
| log_time | 步骤 ⑤ | 录制器收到消息的时间，一定晚于物理事件 |

## 2. 驱动盖戳策略详解

### 策略 A：使用传感器硬件时间（推荐）

质量最好的相机和 IMU 驱动会使用传感器固件提供的硬件时间戳。这些时间戳基于传感器内部的高精度时钟，最接近真实曝光或采样时刻。

```python
# 伪代码：理想情况下驱动如何设置 header.stamp
def on_camera_frame(hardware_timestamp_ns: int) -> None:
    # hardware_timestamp 来自相机固件，需要转换到 ROS 时钟域
    ros_time = convert_hardware_to_ros_time(hardware_timestamp_ns)
    msg.header.stamp = ros_time  # 最接近真实曝光时刻
    publisher.publish(msg)
```

**前提**：传感器硬件时钟必须与主机时钟同步（见第 4 节）。

### 策略 B：使用主机收到时间

简单驱动的常见做法。时间戳是消息到达主机驱动程序的时刻，包含传输延迟：

```python
# 伪代码：简单驱动的时间处理
def on_camera_frame(frame_data: bytes) -> None:
    msg.header.stamp = node.get_clock().now()  # 主机时间，有传输延迟
    publisher.publish(msg)
```

**问题**：USB 传输延迟可达 1-30ms，网络传输延迟更大。如果多个传感器都这样做，它们之间的相对时间误差可能达到几十毫秒——对多传感器融合来说是灾难性的。

### 如何判断你的驱动用哪种策略

```bash
# 1. 录制一小段数据
timeout --signal=INT 10s ros2 bag record -a -o timing_test

# 2. 检查 header.stamp 和 log_time 的差值
python3 analyze_timing.py timing_test
```

```python
"""分析 header.stamp 和 log_time 的差值，推断驱动盖戳策略。"""
from pathlib import Path
from collections import defaultdict

from rosbags.highlevel import AnyReader


def analyze_timing(bag_path: Path) -> None:
    delays: dict[str, list[float]] = defaultdict(list)

    with AnyReader([bag_path]) as reader:
        for connection, log_time_ns, rawdata in reader.messages():
            msg = reader.deserialize(rawdata, connection.msgtype)
            header = getattr(msg, "header", None)
            if header is None:
                continue

            stamp = header.stamp
            stamp_ns = int(stamp.sec) * 1_000_000_000 + int(stamp.nanosec)
            delay_ms = (log_time_ns - stamp_ns) / 1_000_000
            delays[connection.topic].append(delay_ms)

    print("Topic | Mean delay (ms) | Max delay (ms) | Samples")
    print("------|-----------------|-----------------|--------")
    for topic, values in sorted(delays.items()):
        mean_d = sum(values) / len(values)
        max_d = max(values)
        print(f"{topic} | {mean_d:.1f} | {max_d:.1f} | {len(values)}")
```

**判读**：
- 延迟稳定在 1-5ms → 很可能用了硬件时间。
- 延迟在 5-30ms 且波动大 → 可能用了主机收到时间。
- 延迟为负值 → 时钟域不同（如使用了仿真时间但驱动用了系统时间）。

## 3. 多传感器时间同步

### 问题场景

双臂机器人做抓取任务，头部相机和腕部相机需要时间对齐：

```text
如果两个相机的 header.stamp 都来自各自的主机收到时间，
且 USB 传输延迟不同（头部 5ms，腕部 15ms），
那么同一时刻拍到的两帧图像，header.stamp 会差 10ms。

→ 多传感器融合或最近邻匹配会出现错位。
```

### 你的 Orbbec 数据是怎么做的

你的 `数据采集样本/` 中的 manifest 提供了极好的多设备同步信息：

```json
{
  "synchronization": {
    "topology": "star",
    "clock_sync": "Orbbec Context.enable_multi_device_sync",
    "clock_sync_interval_ms": 60000,
    "paired_frame_sets_observed": 2096,
    "pairs": {
      "secondary_1": {
        "paired_frame_sets_observed": 2097,
        "color_timestamp_abs_delta_us": {
          "mean": 126.2,
          "max": 773
        }
      }
    }
  }
}
```

这说明：
- **星型拓扑**：1 个 primary 相机作为主时钟源，4 个 secondary 与之同步。
- **硬件级同步**：使用 Orbbec SDK 的 `enable_multi_device_sync`，不是软件层面的时间匹配。
- **同步质量极高**：secondary_1 的彩色帧时间偏差 mean=126µs、max=773µs——不到 1ms，远优于软件同步。
- **定期重同步**：每 60 秒重新校准时钟，防止漂移。

> 对比：ROS 2 中软件级多相机同步通常只能达到 5-20ms 精度。你的 Orbbec 硬件同步达到了 < 1ms，这非常适合高精度多视角操作任务。

### 在 ROS 2 中实现多传感器同步

如果不用硬件同步，ROS 2 有几种软件方案：

```text
方案 1：message_filters.TimeSynchronizer
  → 严格按 header.stamp 匹配多个话题
  → 适合帧率一致且时间戳质量好的传感器

方案 2：message_filters.ApproximateTimeSynchronizer
  → 允许时间偏差，按最近邻匹配
  → 适合帧率不同或时间戳有抖动的场景

方案 3：自己在 bag 后处理中做最近邻匹配
  → 你前置计划第三周学的方案
  → 最灵活，适合离线分析
```

## 4. 时钟同步方案对比

| 方案 | 精度 | 适用场景 | 复杂度 |
|------|------|---------|--------|
| **硬件触发线** | < 1µs | 工业级多相机系统 | 高（需要硬件接线） |
| **PTP (IEEE 1588)** | < 1ms | 多机器人、分布式系统 | 中（需要 PTP 兼容硬件） |
| **Orbbec SDK 同步** | < 1ms | Orbbec 多相机系统 | 低（SDK 内置） |
| **NTP** | 1-50ms | 单机器人、对精度要求不高 | 低（系统自带） |
| **chrony** | 0.1-10ms | 替代 NTP，精度更好 | 低 |
| **无同步（各自系统时钟）** | 不可控 | 不推荐 | 无 |

### PTP (IEEE 1588) 基础

PTP 是硬件辅助的精确时钟同步协议，可达亚微秒精度：

```bash
# Linux 上使用 linuxptp 包
sudo apt install linuxptp

# 启动 PTP 从时钟（网卡需要支持硬件时间戳）
sudo ptp4l -i eth0 -H -m

# 将系统时钟同步到 PTP 主时钟
sudo phc2sys -s eth0 -c CLOCK_REALTIME -O 0 -m
```

ROS 2 的 `use_sim_time` 和 PTP 不冲突——PTP 同步的是系统时钟，`use_sim_time` 使用的是 `/clock` 话题提供的仿真时间。

### ROS 2 的时钟域

```text
系统时钟（use_sim_time=false）
  ↓
  ros2 bag record 的 log_time ←── 来自系统时钟
  ↓
  如果传感器驱动用 ROS 时间（now()）→ 也来自系统时钟 → 一致

仿真时钟（use_sim_time=true）
  ↓
  /clock 话题发布仿真时间
  ↓
  节点 now() 返回仿真时间
  ↓
  如果传感器是真实的（不是仿真）→ 驱动可能用系统时间 → 不一致！
```

> **常见坑**：使用 `--use-sim-time` 录制真实传感器数据时，如果驱动不使用 ROS 时钟，时间域会不一致。真实硬件采集通常不用仿真时间。

## 5. 相机驱动的关键参数

以 ROS 2 中常见的相机驱动为例：

```yaml
# camera_params.yaml
camera_driver:
  ros__parameters:
    # 分辨率和帧率
    width: 1280
    height: 720
    fps: 30

    # 时间戳来源
    use_sensor_timestamps: true   # 关键！true=硬件时间, false=主机时间

    # 硬件同步
    external_trigger: false       # true=使用外部触发线
    trigger_mode: "master"        # master/slave/software

    # 曝光
    exposure_mode: "auto"         # auto/manual
    exposure_time: 10000          # 微秒，手动模式时生效

    # 格式
    pixel_format: "MJPG"          # MJPG/YUYV/Bayer
    output_encoding: "rgb8"       # 发布到 ROS 的编码
```

`use_sensor_timestamps` 是影响时间戳质量的最重要参数。设为 `true` 时，还需要确保传感器时钟与主机同步。

## 6. 时间同步质量评估指标

在你的数据质量报告中，应该包含以下时间同步指标：

```python
from dataclasses import dataclass


@dataclass(frozen=True)
class SyncQuality:
    """多传感器同步质量报告。"""
    # 配对帧数
    paired_frames: int

    # 帧间时间偏差（微秒）
    mean_delta_us: float
    max_delta_us: float
    p99_delta_us: float  # 99 分位

    # 异常帧比例（偏差超过阈值的帧）
    outlier_ratio: float  # 例如 delta > 5ms 占比

    @property
    def is_good(self) -> bool:
        """硬件同步质量标准：mean < 1ms, p99 < 5ms, outlier < 1%。"""
        return (
            self.mean_delta_us < 1000
            and self.p99_delta_us < 5000
            and self.outlier_ratio < 0.01
        )
```

你的 Orbbec manifest 已经提供了这些指标——secondary_1 的 mean=126µs、max=773µs，远优于 `is_good` 的标准。

## 7. 对数据流水线的影响

| 时间同步质量 | 对训练的影响 | 数据处理策略 |
|------------|------------|------------|
| 硬件同步（< 1ms） | 几乎无影响 | 直接按帧索引对齐 |
| 软件同步（1-10ms） | 轻微影响 | 最近邻匹配 + 10ms 容差 |
| 无同步（> 20ms） | 严重影响 | 需要插值或大幅丢弃不匹配帧 |
| 时钟域混乱 | 数据不可用 | 需要重新采集 |

**在你的 manifest 中记录**：
- 时间同步方案（硬件/PTP/NTP/无）。
- 同步质量指标（mean/max delta）。
- 时间戳来源（硬件/驱动/系统）。
- 是否使用 `use_sim_time`。
